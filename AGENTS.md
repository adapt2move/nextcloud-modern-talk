# Contributor and agent rules

Read [current state](docs/status.md), [product requirements](docs/product/README.md), [quality gates](docs/quality/verification.md) and [architecture](docs/architecture/README.md) before changing behavior. The accepted specification input is `adfb44a2aab2e29ba6574c9dacc09475c534bccf`; preserve [attributed review history](docs/reviews/product-spec-review-r2.md).

1. **Precedence:** explicit user decisions → accepted product and quality requirements → accepted architecture decisions → design flows/tokens → illustrative screenshots/prototypes. Report a conflict; do not silently weaken a requirement or change an accepted source to hide it.
2. **Gate order:** `G.SPEC` has PM acceptance. `G.BOOT` is pending independent review and PM acceptance. Only contracts, minimal composition and bootstrap checks are authorized before that acceptance. Full renderer, network, vault, media and product implementation must wait. A compiler pass does not accept a gate.
3. **Deep Modules:** give each consequential decision one owner with a small interface. Keep wire formats, credentials, storage transactions, timers and media details behind that owner. Prefer a cohesive private module over another facade crate. Do not add a generic event bus, plugin system or empty feature-per-crate hierarchy.
4. **Boundaries:** follow the [three-package graph](docs/architecture/decisions/002-deep-modules.md). GPUI views consume bounded snapshots and typed intents/errors. They perform no network/vault/database/media I/O and hold no secrets. Use account/host/conversation/runtime/call scopes; obsolete completions grant nothing. Every queue/cache/task needs a finite bound, cancellation, overload behavior and a resource owner. Frames never enter chat/event serialization. Unimplemented paths return unsupported/unconfigured, never fake success.
5. **Mandatory IST update on every behavioral, module or configuration change:** update `docs/status.md` and the affected contract/decision in the same change, stating actual behavior, limits, verification performed and missing evidence. Reconcile README, examples, feature inventory and test/release claims; explicitly record “no product feature status change” for infrastructure-only work. Do not leave stale counts, routes, commands or parity claims. Planned → Implemented → Verified follows [Q.VER-04](docs/quality/verification.md#qver-04--feature-parity-traceability).
6. **Independent roles:** the PM coordinates and accepts; delegated contributors implement; separately delegated reviewers assess architecture/modules, function/compatibility, performance and coarse security on the exact candidate. Authors do not approve their own work. Preserve objections and remediation reports. Do not spawn additional agents unless the assigned brief explicitly authorizes them. Respect concurrently assigned paths; do not overwrite another author's changes.
7. **Validation:** use the [canonical commands](docs/architecture/README.md#validation). Run builds/tests/services through the assigned agent-dev-box session when required by the work environment. The designated lab owner alone provisions and tears down disposable services; the designated verifier runs combined checks. Never substitute a host run when prohibited. Report unrun checks plainly. Linux checks do not qualify macOS Keychain, GPUI, capture or performance.
8. **Public hygiene:** EUPL-1.2; dependencies need version/license/provenance review. Never commit credentials, production data, private paths, runtime dumps or secret-bearing fixtures. Tests use synthetic identities. Follow [SECURITY.md](SECURITY.md). No commits, publishing, repository creation or pushes beyond the assigned authorization.

For review handoffs, name files, decisions, requirement/test IDs, exact commands/results, source evidence, unresolved assumptions and the next owner. Never describe a mockup, stub, API health check or compilation as a working native client.
