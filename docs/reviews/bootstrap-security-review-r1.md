## BSR1-01 — High: explicit identity choices and recovery authority are missing from the port

**State: open. Owner: separately delegated identity/architecture contributor; independent verifier owns contract execution.** This is the security assessment of the same underlying interface defect recorded as **BAR1-01** by the separate architecture reviewer, not a second implementation task. Affects AUTH-003–005/007/008, Q.SEC-02–05, V.AUTH.STORE-01–06 and V.AUTH.LOSS-03. Exact locations: [ports.rs](../../crates/talk-core/src/ports.rs), lines 60–64 and 90–114; [ADR-002](../architecture/decisions/002-deep-modules.md), lines 27 and 32–34; [ADR-003](../architecture/decisions/003-credential-lifecycle.md), lines 12–19, 35–50 and 69–71.

**Static reproductions/preconditions:**

1. Let valid older credential P coexist with staged N whose write is uncertain. The user deliberately cancels N and retains P. ADR-003 requires an atomic abandoned-N cleanup record plus `Eligible(P)`. `IdentityCommand` has no command carrying that choice. `Activate(StoreIntent)` is specified to activate N; suppression makes all generations ineligible; reconciliation cannot change the chosen disposition. Session-only also lacks the explicit choice coupling abandonment, durable suppression and authorization of the new in-memory runtime. A cancellation token cannot safely infer either choice.
2. Restore or reconcile on cold start before validated runtime authorization exists. `OperationContext` and `Resolve(AccountScope)` require `RuntimeGeneration`, while ADR-003 defines that as an already validated authorization lifetime. No pre-runtime recovery context or alternative authority sequence is specified. Constructing an arbitrary ID does not establish the contract's authorization precondition.
3. Confirm account rejection, close admission and cancel its shared token. ADR-002 says adapters check the context before dispatch/after completion; identity suppression still takes that context. No bounded supervisor authority surviving the rejected runtime is defined for suppression or late-writer reconciliation. A fresh token/bypassed scope check would be a new lifecycle decision, not an implementation of an existing one. `MediaPort::stop` explicitly separates its shutdown lifetime, showing the needed distinction is already understood elsewhere.

**Expected:** these operations are expressible under explicit, narrowly scoped authority, with committed disposition acknowledged before replacement activation and recovery continuing after runtime loss. **Actual:** prose promises the transitions while the public seam cannot select them or supply the defined lifetime. Choosing an undocumented workaround risks restoring the wrong generation, treating cancellation as consent, or abandoning durable suppression. This is a high-impact bootstrap contract gap; no current credential leak is claimed because every concrete adapter is unconfigured.

I identified the missing explicit choices and cancellation-lifetime problem before the PM supplied the [architecture report](bootstrap-architecture-review-r1.md). I then independently re-read its cold-restoration case against the candidate signatures and ADR definitions and agree with that additional manifestation. The shared source evidence is attributed; this report's security verdict is independent.

**Required correction:** define pending-attempt, restoration/recovery and authenticated-operation contexts and their allowed operations. Provide an explicit session-only/cancel-and-retain command or equivalent typed choice, correlated with exact account/attempt/N/P/operation identity and committed acknowledgement. Assign bounded supervisor ownership for suppression, settlement and cleanup that cannot be cancelled with the runtime it is closing. Preserve nonsecret metadata, exact-N deletion, older-item protection and no activation by late completion. Do not implement the vault merely to close this contract finding.

**Acceptance:** separately executed contract cases cover cold restoration without a live runtime; uncertain N → deliberate session-only; uncertain N → deliberate retention of P; post-cancellation suppression; late settlement that cannot activate N; and preservation of other accounts. No fabricated runtime or cancellation-as-consent shortcut. Keep actual Keychain/crash/power-loss tests as later native qualification. Update ADR/IST in the new candidate and obtain independent recheck. Author response/remediation commit: **none supplied**. Dynamic reproduction/recheck: **not run by this reviewer**.

## Coarse-security assessment

The credential design correctly separates runtime, login-attempt, operation and vault-item identity. It specifies committed nonsecret intent before a write, new N distinct from retained P, account-wide suppression before session-only activation, only committed deliberate retention restoring P, and no eligibility by vault enumeration. Abandonment does not imply writer settlement; exact-N absence is insufficient until late writers cannot recreate it. Missing/corrupt metadata blocks recovery, and failed suppression cannot support a false session-only restart promise. SQLite durability settings are selected but explicitly require native/VFS qualification. Keychain has no assumed durable operation-query oracle; an unproved post-crash barrier leaves the path blocked with residual-warning state. BSR1-01 concerns how those correct decisions cross the actual service seam, not reopening QR1-01's specification closure.

Account rejection is narrowly scoped to a qualified same-origin, uncached authenticated probe and well-formed unauthorized OCS envelope, with expected user binding. Generic 401/403, room/HPB expiry and transport failures do not become account revocation. The actor closes admission/generation and local publication independently of leave, vault or metadata completion; 250 ms publication and 1 s release are requirements with a 750 ms helper escalation and observable unconfirmed-release failure. Other accounts and permitted drafts survive. Native teardown and warning delivery remain unimplemented. Focused checks confirmed the unauthorized constant and v2 HTTP mapping in the pinned [OCS controller](https://github.com/nextcloud/server/blob/ba900af933e61ffa005315b09d6454bfbbcbcc81/lib/public/AppFramework/OCSController.php), [NC34 response](https://github.com/nextcloud/server/blob/77e3cab12d2215bf94d6de67f23b98ed7bad236e/lib/private/AppFramework/OCS/V2Response.php) and [NC35 response](https://github.com/nextcloud/server/blob/ba900af933e61ffa005315b09d6454bfbbcbcc81/lib/private/AppFramework/OCS/V2Response.php); this does not qualify live app-password rejection.

Policy source bundles preserve account/local/host/room/session provenance and unknown state. The minimum `Gate` and public lease constructor are explicitly preconditioned primitives, not complete grants; no current adapter synthesizes a qualified observation. Both-family full capability refresh covers E2EE/grid policy; local grid authority and federation/guest unsupported states are explicit. `S=2 s` is a deployment prerequisite, not assumed from HTTP success. Missing propagation/source evidence blocks the affected native call path. `F/R/D/S/E = 15 s/10 s/3 s/2 s/250 ms` and request-start-based expiry are arithmetically consistent; earliest expiry, failed/partial/hash-only reads, out-of-order generations, sleep epochs and half-open control loss cannot renew authority. Unknown membership/consent/encryption leaves locally; grid-only expiry blanks/unsubscribes remote video while separately fresh audio may continue. Actual enforcement remains unproved.

Focused primary reads confirmed that both pinned [Talk24 capability emitter](https://github.com/nextcloud/spreed/blob/17afc250cf5fe3f7e016739dd3d7a3a44bb2cb79/lib/Capabilities.php) and [Talk25 emitter](https://github.com/nextcloud/spreed/blob/f35255ab86f31e8ee894641f6970a09ce4b90927/lib/Capabilities.php) expose the cited policy fields/local grid list and condition E2EE support on external signaling. Both [Talk24 settings](https://github.com/nextcloud/spreed/blob/17afc250cf5fe3f7e016739dd3d7a3a44bb2cb79/docs/settings.md) and [Talk25 settings](https://github.com/nextcloud/spreed/blob/f35255ab86f31e8ee894641f6970a09ce4b90927/docs/settings.md) mark E2EE/grid enforcement as not changing the hash. Research pins remain distinct from released fixtures. Internal/HPB source documents were inspected for continuity scope; no universal freshness authority or complete released-profile compatibility was inferred. The entirety of upstream routing/permission code was not independently re-audited.

No secrets, wire routes, raw provider messages or native handles occur in the renderer contract. Errors use allowlisted enums; text/pages are bounded; the diagnostic discards its sole snapshot and prints fixed absence statements. TLS/origin/redirect, attachment/quarantine, native rich-content, cache and canary-log rules remain requirements rather than implemented defenses. BAR1-02's private data imports and checker restriction do statically prevent intended structured enum use; I agree with the interface concern after inspecting `ui.rs` and checker lines 101–110, but make no separate security finding or executed claim.
