# ADR-005 — Pinned native WebRTC and bounded media ownership

Status: proposed for `G.BOOT`, 2026-10-18; remediation of BSR1-02 and BPR1-01, **fixed pending independent verification**. The accepted specification and [mandatory handoff](../../reviews/product-spec-review-r2.md#mandatory-bootstrap-handoff) remain authoritative. This selects an engine and binding without linking or implementing them. It is not distribution approval, native feasibility, interoperability, security or performance evidence. All 140 features remain Planned; G.BOOT is unaccepted.

Companions: [allocation contract](../media-allocation.md), [public source manifest](../evidence/native-media-sources.json), and [remediation report](../../reviews/bootstrap-remediation-r1.md). The manifest attributes source retrieval to the separate media proposal author; integration does not turn those reads into an independent audit or complete SBOM.

## 1. Engine, provenance and codec decision

Select **upstream WebRTC native C++ (“libwebrtc”)**, source commit **`a306485b7fc0fe38dd2651420e383f92f196cd77`**, from the [canonical upstream repository][W-commit]. Its tree is `f1bb4132a097a0c65c00f1a0f425a9b403798116`. This is a rolling upstream research/source baseline, not a tagged SDK release, security-cleared release or prebuilt binary. The [README][W-readme] identifies the native API and canonical repository. Pin the source and its [DEPS][W-deps], not a floating branch or an unrelated download labelled “WebRTC.” No binary was downloaded or built.

Use the corresponding dependency graph, including libvpx **`5e680f30801d03c21078f8c4b772464752516211`** and Chromium `third_party` **`8a83e63525b495aa7f35648a3b4b676279deb864`**. The latter contains an Opus copy whose [provenance record][TP-opus] identifies upstream `55513e81d8f606bd75d0ff773d2144e5f2a732f5` **plus local modifications**; the actual selected bytes are the Chromium-pinned copy. The manifest records hashes of retrieved files. These observations are not a complete dependency SBOM or a reproduced build closure.

Select **software VP8, 8-bit 4:2:0, and Opus** for the first qualification profile: camera 1280×720 at 30 fps; screen 1920×1080 at 10 fps; Opus 48 kHz mono, 20 ms frames. Baseline cameras remain active while sharing. Initially select one spatial/temporal rendition; additional simulcast encoders/layers need separate counted reservations and workload evidence. This is an engineering profile to qualify, not evidence that either Talk deployment will negotiate it or meet CPU/power targets. Hardware codecs and other codec profiles require their own admission and distribution review. A peer that cannot negotiate the qualified profile remains unsupported, rather than invoking an unreviewed fallback.

The engine's [BSD-style three-clause license][W-license] and [additional patent grant][W-patents], libvpx's [license][VPX-license]/[patent terms][VPX-patents], and Opus's [copyright and patent references][TP-opus-license] must accompany the selected build's attribution review. Preserve the project's EUPL-1.2 license. These terms make this a plausible dependency direction; they do not establish clearance for every transitive component or codec patent/distribution obligation. Before distribution, retain the complete source/dependency/toolchain/SDK manifest, patch hashes, binary hashes, SBOM, notices, applicable source obligations, signing and notarization evidence. Verify what the binary actually includes: excluding a codec from negotiation does not remove its bundled code or obligations. Upstream itself flags separate H.264/OpenH264/FFmpeg licensing concerns in [webrtc.gni][W-gn]. Do not copy Talk's AGPL application code into the EUPL implementation; use protocol evidence and independently authored adapters, with separate review of any future reused code.

**Why this engine:** its [factory API][W-factory] composes audio device/processing/codec services with replaceable video codec factories, and its [PeerConnection API][W-pc] supplies SDP/ICE/TURN integration points. This reduces the amount of conferencing machinery the project must assemble. It is a judgment about implementation scope, not a claim that libwebrtc is smaller or faster. Serious alternatives considered:

- **GStreamer `webrtcbin`**, inspected at `82cd8b72f719a87182104b879482f15b7888c71f`, supplies native SDP/ICE/DTLS and RTP pipeline integration. It remains credible, but requires a selected capture/codec/audio-processing pipeline, plugin inventory and equivalent lifetime/allocation controls; no project evidence gives it a performance advantage. See its [implementation/API description][ALT-gst].
- **libdatachannel**, inspected at `bdc5ff28e9d3b863144c94a677ecf5bf043aaf15`, supplies a native WebRTC transport and C bindings under MPL-2.0. Its [examples][ALT-dc-examples] compose media capture/processing with GStreamer or encoded samples. That leaves more conferencing media integration to this project than the selected factory approach. See its [scope and license][ALT-dc].

## 2. Binding and process boundary

Choose a **project-owned, versioned IPC binding from Rust to a native C++/Objective-C++ helper**, using libwebrtc's C++ API only inside that helper. This is the binding decision: no third-party Rust WebRTC wrapper is selected and no C++ object layout or pointer crosses the process boundary. Rust/GPUI remains the application architecture; the native helper contains the media stack and platform bridges. This is neither a WebView nor a JavaScript runtime.

`talk-adapters::media` owns the Rust supervisor/client and validates bounded IPC. The future native helper is an implementation of this owner, not a new product service or public plugin API. The existing three-package Rust graph, path-only lockfile and workspace-wide unsafe prohibition remain unchanged in bootstrap. Later native build integration and any unsafe macOS IPC/surface-import wrapper require a narrowly scoped, independently reviewed exception; no blanket relaxation of `forbid(unsafe_code)`. The helper owns all C/Objective-C framework FFI: native refcounts, ARC/block captures and Core Foundation retain/release must balance under explicit stop/drain. Capture/audio callback buffers are borrowed; retaining a sample requires an owned, charged reference. Rust receives IDs and safe lease wrappers only. Process separation contains hangs and lifetime failures; it is not a claim of an implemented macOS security sandbox.

The future private protocol has typed operations equivalent to `CreateSession`, `ApplySignaling`, `SetAuthority`, `SetTrackIntent`, `ReleaseSurface`, and `RevokeAndDrain`. It carries account/runtime/call/stream/format-generation identities, operation IDs and finite deadlines. Ordinary records stay ≤8 KiB; a complete SDP is ≤64 KiB, passed through a bounded chunk/lease facility charged to the control arena. No allocation is sized directly from an unchecked length. Unknown protocol versions, mismatched scope, duplicate/stale handles or exhausted reservations fail closed. There is one nonqueued revoke flag per call. Frames use leased shared backing, never serialized chat events or `ViewSnapshot` bytes.

At most two account-scoped media helpers exist application-wide, with at most one call/prejoin slot and one helper per account. One publishing call per account and eight configured accounts remain the existing limits. A same-account preview-to-call transition reuses its slot/helper; another preview or call cannot acquire a second slot for that account. A preview consumes a slot. One account cannot retain an old helper and start an uncharged replacement. A separately scheduled runtime watchdog, outside GPUI and the media helpers, owns their birth identities, expiry/revoke state and termination authority. It holds no Nextcloud password or media key. Native process/signing/permission feasibility is unproved.

| Resource | Single owner and lifetime rule |
| --- | --- |
| Factory, PeerConnections, transceivers, tracks, codec instances | Helper `CallSession`; create/destroy on the required executors. At most 12 PeerConnections and 24 RTP transceivers per call, within the allocation contract. Factories/custom codec implementations cannot silently add an unreserved codec/layer. Threads outlive their queued work and dependent objects. The selected factory has network/signaling threads; do not assume a separately supported worker thread from older SDK examples. |
| Native capture and audio handles | Helper platform owner: AVFoundation camera/permission bridge, ScreenCaptureKit screen bridge, and qualified macOS audio device module. Device/source selection and explicit intent precede opening. One local microphone, camera and screen per call; no cross-account capture sharing. Exclusive device leases return `Busy` if another owner holds an incompatible lease. Ringing opens no device and requests no permission. |
| Signaling and transport | Nextcloud adapter retains authenticated internal/HPB control connections and account credentials. Helper owns bounded media ICE/TURN/DTLS/SRTP state. Only authorized, call-scoped server configuration and ephemeral TURN credentials enter private IPC. Validate endpoint scope, TURN TLS certificates and SDP fingerprint/DTLS bindings; never use insecure certificate bypasses to make interoperability work. |
| DTLS/SRTP and future E2EE state | Helper transport/crypto owner, distinct by account/call/peer/key generation. DTLS private keys remain in engine-owned objects; no export to core/UI. A future Talk E2EE owner holds bounded per-participant sessions/key rings (≤8 remote call participants, including silent/hidden participants; ≤16 receive-key slots per participant), zeroizes owned secret buffers on retirement where supported, and destroys sender/receiver crypto references only after callbacks drain. Library/OS copies and process death do not prove secure erasure. |
| Callbacks and borrowed buffers | Helper callback registry retains each context until unregister plus quiescence. Incoming pointers/spans are borrowed only for callback duration; retain a counted native reference or make a separately reserved copy before returning. No Rust borrow or C++ exception crosses IPC; exceptions/errors become bounded allowlisted failures. Callbacks perform no UI work and cannot grant authority. |
| Shared CPU/GPU surfaces | Allocation owner issues immutable generation-tagged leases; renderer owns only its lease and GPU completion fence. Charge unique backing once across processes and count distinct copies separately. Producer reuse/free requires all native references, IPC leases and GPU uses to finish. A renderer-held handle cannot become a media/session capability. |

The API has specific, limited shutdown assurances: [PeerConnection `Close`][W-pc] terminates its use of the construction observer after completion; [sender][W-sender]/[receiver][W-receiver] observers must be detached before destruction. These do **not** prove all codec, capture, transformer or OS callbacks have drained. The binding must establish those barriers separately.

## 3. Talk protocol and encryption applicability

Library selection supplies mechanisms, not product support. Every profile remains `Unconfigured`/unsupported until its exact release, deployment, policy and native evidence qualifies it.

| Path | Verified source mechanism | Project-owned work and blocker |
| --- | --- | --- |
| Internal signaling | Talk24/25 [settings/internal-signaling docs][T24-signaling] expose settings, STUN/TURN credentials and the external/internal distinction; the internal protocol section is incomplete. Both pinned browser [peer implementations][T25-peer] provide additional SDP/candidate evidence. | Implement authenticated OCS session/signaling adapter, offer/answer ordering, stream identity, SDP compatibility and ICE restart. First qualification is direct calling; internal group fan-out needs separate allocation and network evidence. No internal E2EE support is inferred. |
| HPB + TURN | Pinned [HPB protocol][HPB] specifies self-session publication, remote `requestoffer`, separate video/screen identities and candidate exchange. libwebrtc exposes corresponding native transport primitives. | Implement HPB hello/room/session/resume and publisher/subscriber orchestration, media/control correlation and forced-relay handling. Preserve separate screen and camera tracks and stricter grid policy. Pin actual HPB/TURN artifacts for later tests. API similarity is not interoperability proof. |
| Talk E2EE | Sender/receiver [frame transformers][W-transform] and [frame encryptor][W-encryptor]/[decryptor][W-decryptor] interfaces exist in libwebrtc. Talk's pinned [key-management code][T25-encryption] uses Olm-based sessions and participant-driven key updates; its [frame worker][T25-framecrypto] has its own VP8/Opus clear-header, AES-GCM and trailer scheme. Retrieved T24/T25 versions of these two files are byte-identical. | Build and independently review the Talk key protocol, compatible cryptographic dependencies, frame transform, key rotation/participant binding, authentication failure and downgrade prevention. Choose the transformer path for wire-format work; native generic/SFrame APIs are not automatically Talk-compatible. No E2EE implementation or cryptographic dependency is linked by this decision. Required or unknown required E2EE blocks joining/publication. A non-E2EE profile is eligible only when fresh policy explicitly permits it. |

For E2EE, the selected headers are extension points, not guarantees that a concrete factory path invokes them: callback routing, bypass paths, framing and bounded expansion must be tested. Outbound missing-key or transform failure drops the frame and closes affected admission; it never falls through to transport-only encryption. Authentication and bounds checks precede native decode of decrypted content. Keep DTLS-SRTP regardless of the additional E2EE layer. Talk's own implementation behavior is evidence of its wire format, not authority to weaken this product's no-downgrade rule.

The accepted research pins remain T24 `17afc250cf5fe3f7e016739dd3d7a3a44bb2cb79` and T25 `f35255ab86f31e8ee894641f6970a09ce4b90927`; they are distinct from released-tag/artifact evidence. Required later runs cover exact NC34.x/Talk24.x and NC35.x/Talk25.x patches, internal/HPB/TURN, policy freshness and the relevant CT/V.MEDIA cases. Guest/federated profiles remain separately blocked under ADR-004. The existing `F/R/D/S/E` values and source qualification rules are unchanged.

## 4. Stop, drain and generation change

The shutdown owner outlives the account runtime/call it is closing; cancellation of that runtime cannot cancel teardown. No remote leave, vault, renderer or ordinary queue is on the stop critical path.

1. At restrictive observation/expiry/leave `t0`, revoke call admission and the publication generation; set priority stop and discard unsent media. A proposed gate at the helper's final transport-send boundary checks authority immediately before handoff, including retransmissions/queued sends. `track.enabled = false`, dropping a UI tile or awaiting `Close` alone is insufficient. Gate placement and all bypass paths require qualification; already handed-off packets cannot be recalled.
2. Maintain **250 ms maximum publication stop**. The independent watchdog reads the same monotonic expiry/revoke state. If the qualified closure path is not acknowledged by **200 ms**, initiate helper termination immediately, leaving 50 ms of the required publication deadline for qualification. This is an additional early escalation: the existing 750 ms device-release escalation cannot by itself satisfy 250 ms when a worker hangs. No OS scheduling/termination guarantee is asserted.
3. On owned executors, stop microphone/camera/screen sources, detach sinks/observers and transforms, stop audio recording/playout, close PeerConnections and transports, and unregister callbacks. Keep contexts, keys and backing alive until callback/task barriers, codec release and surface fences settle. Late completions may release their exact old resources only; they cannot publish, change current state or install new keys.
4. If device release remains unconfirmed at **750 ms**, terminate the account helper if not already terminated. By **1,000 ms**, require independently qualified evidence of capture stop/device release. A stopped IPC message, process exit or invisible preview alone is insufficient. An observed overrun fails qualification; missing observation is incomplete. Retain `CaptureReleaseDeadlineExceeded`, closed admission and the persistent “Gerätefreigabe nicht bestätigt” state. Other accounts are not terminated. Recovery requires repair and deliberate rejoin; no automatic unmute/camera/share restart.
5. Revoke presentation leases, blank obsolete surfaces and reclaim only after reference/fence settlement. Old-generation resources remain charged until actual release, including mappings held by a stalled renderer after helper exit. No reset-to-zero or new full pool while the old one remains. Stalled reclamation rejects new admission; do not free memory still in use. Whether retained native buffers can keep capture/device resources alive is a mandatory macOS test. An implementation that cannot release the device within 1 s with a stalled renderer does not qualify.

Record synthetic scope/clock/birth identities, trigger/expiry, final publication, stop request, quiescence, device observation, helper exit and outstanding byte/lease counts. No SDP, candidates, keys, payloads or private paths in telemetry. Account-loss, sleep/wake and half-open-control cases retain the accepted ADR-004 semantics. The watchdog must remain effective during UI, signaling and media executor stalls, and detect control-channel EOF/owner death; its own failure closes admission. These are acceptance requirements, not measured timings.

## 5. Finite admission and the unresolved native hooks

Adopt [the allocation contract](../media-allocation.md) as part of this decision. It derives **140 MiB** of controlled buffers for direct video, **268 MiB** for the four-person conference, **388 MiB** for either required conference+screen direction, and **572 MiB per maximal call slot / 1,144 MiB for two slots**. These are conservative reservation maxima, not eager allocations, RSS/footprint results or new workload budgets. All local preview, reference, capture, conversion, in-flight, shared and renderer/GPU retention is charged. An additional finite engine-private allowance is specified separately and is explicitly unproved.

There is no verified universal allocation hook in the selected engine. In particular:

- [VideoDecoder settings][W-decoder] place a resolution obligation on the caller and allow a pool-size setting to be ignored by a decoder without that pool. The [VP8 wrapper][W-vp8] calls libvpx decode before creating/copying its output-pool buffer. Its output-pool setting does not cap libvpx reference/scratch allocations.
- Pinned libvpx has a real **pre-initialization VP8 keyframe size guard** under `CONFIG_SIZE_LIMIT` in [vp8_dx_iface.c][VPX-decoder] and a [`--size-limit=WxH` configure option][VPX-configure]. However, the selected Chromium [generator][TP-generator] and [arm64 configuration][TP-vpx-config] use **16384×16384**. The pinned [BUILD.gn][TP-build] routes macOS arm64 through that POSIX configuration; its high-bit-depth build capability is not an admitted product format. The required future build must generate and verify **1920×1080** limits, with a stricter per-camera wrapper guard. This needs a reviewed build/configuration patch and new artifact identity, not merely setting `max_render_resolution`. The guard bounds dimensions, not every allocation or allocation count.
- Libvpx's [external-frame-buffer API][VPX-api] states that it currently works with VP9; it cannot be represented as an available VP8 pool hook. [EncodedImageBuffer][W-encoded] also allocates/resizes from supplied sizes. RTP reassembly, pacing/retransmission, encryption expansion and source/GPU allocation can precede a decoder or renderer callback.

Therefore **unmodified upstream is not qualified for this contract**. Required future work is a bounded decoder/encoder factory wrapper, the verified libvpx size configuration, and reviewed source/allocator integration wherever needed to reserve the specified native backing/scratch/packet bytes **before** allocation. Auditing a fixed allocator path with a proved maximum is acceptable; measuring a peak or killing a helper after excess is not a replacement. If any required path cannot obey the contract, that profile stays blocked. Bootstrap admits **zero media sessions/devices/frames**; selecting the library does not enable it.

## 6. Update ownership and qualification handoff

The **media/platform maintainer** owns this pin, native patches, IPC schema, codec factory inventory, per-allocation ledger and macOS bridges. The **runtime owner** owns watchdog independence and process registration; the **Nextcloud adapter owner** owns signaling and policy-source integration; the **renderer owner** owns surface fences. PM assigns the responsible individuals before native integration. The media maintainer reviews upstream security changes weekly and before each candidate; reachable unresolved findings block the affected profile/release. Updating the engine, DEPS, SDK, codec or patch set creates a new source/artifact identity and renews affected independent reviews; no floating auto-update.

Future qualification must provide:

- Reproducible arm64/macOS 15.7 build/signing/permissions and dependency/license evidence, including exact Xcode/SDK/compiler flags and patched generated codec configuration. No compatibility with that OS is established by these reads.
- Allocation-path inventory and fault injection: oversized/malformed SDP/RTP/VP8/Opus, integer/stride/plane overflow, fragmented frames, decrypt expansion, midstream dimensions, decoder/encoder references, native source queues, allocation denial, callback reentrancy and generation/fence retention. Verify rejection before native allocation, including allocations preceding decoder callbacks.
- Real bidirectional media and screen sender/receiver workloads on both exact server families with internal signaling and HPB/forced TURN as applicable. Verify SDP/track mapping, required E2EE denial, participant changes, reconnect and deliberate intent. Any future E2EE claim needs native known-answer and cross-client key/framing/rotation/failure tests.
- Timestamped 250 ms publication/1 s device-release evidence with UI/helper/transport stalls, saturated queues, dropped leave, old callbacks, account A loss while B continues, sleep/wake and killed helpers. Native permissions and device/packet observers are indispensable.
- Frozen workload reconstruction and complete lifetime/peak/GPU collectors under V.PERF.PEAK/WORKLOAD. Preserve the accepted p95/peak, CPU, power, latency and traffic ceilings; a smaller delivered profile cannot inherit their pass.

## 7. Finding response and remaining evidence

BSR1-02 is addressed by the source/dependency selection, IPC/native boundary and resource/key/callback/update ownership above. BPR1-01 is addressed by the [allocation contract](../media-allocation.md), including finite backing/auxiliary limits, checked pre-allocation reservation and generation/fence retention. Both are **fixed pending independent review** of the integrated candidate; neither is an author-approved gate or runtime result. See the [remediation report](../../reviews/bootstrap-remediation-r1.md) for exact proposal/source identities, integration corrections and executed preliminary checks.

Native integration, exhaustive allocation-path proof, licenses/advisories, device-release/watchdog feasibility, E2EE and released-profile interoperability remain unqualified. A separate profile is additional qualification work, not permission to silently remove accepted parity requirements or substitute a lighter workload. Public WIP publication authorizes none of those claims.
