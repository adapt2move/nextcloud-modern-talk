# ADR-003 — Identity, durable restoration and account loss

Status: proposed for `G.BOOT`, 2026-10-18. AUTH-003–008, Q.SEC-02–05 and V.AUTH.STORE/LOSS are normative. **No Login Flow, vault, SQLite database or recovery worker exists yet.** Core contains only nonsecret contract types and narrow cleanup/admission/correlation checks; none of these constructors or receipts performs storage I/O or establishes authorization.

## Identities and authority

The identity adapter owns browser authorization, pending secrets and vault/metadata transactions. It serializes transitions per account; the application account actor owns authenticated admission. A profile-wide single-writer process lock plus transactional revision comparison prevents two processes from replacing the same account independently. Losing that lock closes admission for restoration mutations, never silently becomes a second writer.

| Identity | Meaning and invalidation |
| --- | --- |
| `AccountId`, `ProfileId`, `HostId` | Random local IDs; persisted nonsecret binding to canonical server base URL including installation path and canonical server user ID. Login name is stored separately from canonical identity. Two users or installations never share a key. |
| `RuntimeGeneration` | Validated in-memory authorization lifetime. Logout, replacement activation or confirmed account rejection permanently closes it. It is not a vault generation or a persisted reusable token. |
| `LoginAttemptId` | One pending browser flow/replacement attempt. Cancellation abandons this attempt without implicitly invalidating a deliberately retained valid older runtime. |
| `VaultGeneration`, `OperationId` | Immutable attempted item identity and provider-operation ledger identity. New save attempts never overwrite old generations. Timeouts/cancellation do not settle a provider operation. |
| `CallGeneration` | One local join/incoming acceptance lifecycle; account scope and conversation-host scope are embedded. Reauthorization cannot reactivate it. |

Future item identity is application namespace `org.adapt2move.nextcloud-modern-talk` + profile + account + secret kind + schema version + vault generation. Labels contain no password, token, invitation credential or server secret. macOS targets application-owned generic-password Keychain records, with synchronization off where supported and access/signing policy qualified. Windows targets user-scoped Credential Manager; Linux targets a qualified Secret Service provider. No platform qualifies by name alone. [Q.SEC-03 primary platform sources](../../quality/security.md#qsec-03--os-vault-contract).

A fresh account reserves its random local account/attempt/N/provider-operation IDs against a validated server binding before browser login. Canonical user binding is established by identity validation, not by reserving these IDs. `RuntimeGeneration` is issued only after validated activation/restoration; it is never invented for this reservation.

Only adapter-private code can materialize an app password or guest/signaling token. Authenticated worker operations use `AccountScope`; pending authorization, recovery and maintenance have separate contexts; the identity owner lends the secret directly to a validated, origin-bound transport operation and releases its temporary buffer. Core, UI, diagnostics, task descriptors and media control receive no secret. Session-only is an explicit user decision; no plaintext preferences, token environment variables, encrypted-file-with-adjacent-key or mock vault can substitute for an OS vault.

## Nonsecret durability decision

Use a separate **SQLite restoration ledger** with a single writer, rollback journal `DELETE`, `synchronous=EXTRA`, and macOS `fullfsync=ON`, subject to native filesystem/power-loss qualification. No SQLite dependency is added at this gate. The selected future SQLite build/VFS and OS must report the effective settings and pass crash tests; unsupported flush guarantees leave restoration unqualified. The decision uses SQLite's [atomic commit model](https://www.sqlite.org/atomiccommit.html) and [documented pragmas](https://www.sqlite.org/pragma.html#pragma_synchronous), not a claim that writes are already durable on arbitrary hardware.

Schema version 1 consists of three logical records updated in one transaction:

- `AccountRestoration`: profile/account/origin/user binding, monotonic record revision, disposition (`Suppressed`, `Unresolved`, or `Eligible(exact generation)`), named retained generation and active attempt ID if any.
- `StoreOperation`: operation/attempt IDs, exact attempted generation, retained generation, phase (`IntentCommitted`, `Dispatched`, `SettledPresent`, `SettledAbsent`, `Abandoned`, `Activated`), settlement evidence and nonsecret error category. Abandonment and writer settlement are independent fields; one must not overwrite the other.
- `CleanupMarker`: exact account/attempted generation, reason, pending settlement/deletion state and last redacted provider code. The older retained item's removal needs a different explicitly authorized operation.

The journal and backups contain **no credentials**. They do contain sensitive account metadata: restrict filesystem access and exclude them from public diagnostics. Each commit compares the expected revision, completes its durable transaction and only then acknowledges the transition. Corruption/missing/inconsistent metadata is `RecoveryRequired`; vault enumeration cannot reconstruct eligibility. Deleting the ledger cannot make a surviving credential restorable. Validate schema and binding before any vault resolution.

## Operations and crash ordering

The public trait in `ports.rs` has exactly four worker methods (plus `availability`). Their context and command/report types live together in `identity.rs`; `OperationContext` remains the shared authenticated-operation context. Internal journal/provider seams and settlement callbacks stay private. Every concrete method on `UnconfiguredIdentity` returns `Unconfigured`.

| Signature | Authority and permitted result |
| --- | --- |
| `attempt(PendingAttemptContext, AttemptCommand) -> Task<AttemptReport>` | `PendingAttemptContext { intent: StoreIntent, deadline, cancellation }` carries account/attempt/N/P/provider-operation identity, **no runtime**. `Authorize` starts/continues a bounded system-browser flow and validates the intended canonical identity without activating it. `Stage`, `ActivateStored` and `ActivateSessionOnly(SessionOnlyCommit)` operate on that same current attempt. `AttemptReport` distinguishes `Authorized`, `Staged` and `Activated`; only explicit activation after revalidation issues a fresh runtime. |
| `restore(RecoveryContext) -> Task<RestoredIdentity>` | `RecoveryContext { account, operation, deadline, cancellation }` requires no live runtime. Load intact committed metadata, select only its exact eligible generation, resolve/validate that item privately against the intended canonical account, then issue a fresh runtime. Missing/corrupt/unresolved/suppressed metadata cannot restore by enumeration. `RestoredIdentity` correlates the recovery operation, account/runtime, exact item and committed record. |
| `resolve(OperationContext) -> Task<IdentityStatus>` | Requires a still-admitted authenticated scope before dispatch and result delivery. Private credential borrowing is limited to a validated origin-bound transport operation; this method returns only redacted state, never a reusable secret/auth object. |
| `maintain(MaintenanceContext, MaintenanceCommand) -> Task<MaintenanceReport>` | The identity supervisor alone supplies `MaintenanceContext::for_supervisor(account, operation, now)`, with a finite 3 s slice and **no runtime or caller cancellation token**. Commands are `Abandon(Abandonment)`, `Suppress(SuppressionCause)`, `Reconcile(StoreIntent)` and `DeleteAbandonedAttempt(StoreIntent)`. Results contain only correlated committed restoration/settlement/cleanup observations, never an activated runtime. Referencing a rejected runtime identifies the loss being settled; it does not grant authenticated authority. |

`StoreIntent.operation` always identifies the original provider writer; `MaintenanceContext.operation` identifies the separate maintenance transition. Reuse a transition ID only to observe/retry that exact semantic decision; a new choice uses a new ID. Every command validates its account/attempt/N/P/writer binding against the owner's registry and ledger before effects; every durable mutation serializes against the current account revision. A stale transition cannot overwrite a newer suppression/retention/activation, and another account's descriptors cannot affect this one. `MaintenanceCommand::is_scoped_to`, `PendingAttemptContext::admits` and acknowledgement predicates check only their named correlations/time bounds, not the absent registry, provider or database.

`Abandonment::new(intent, choice)` rejects `N == P`, retention of a generation other than the named P, and a retained runtime from a different account. Choices are explicit: `SessionOnly`, `Cancel`, or `RetainPrevious { generation, validation }`. `RetentionValidation::CurrentRuntime(scope)` must still be admitted, bound to P and canonically valid at commit; `RevalidateStored` is an explicit cold-recovery request to validate that exact stored P privately, not asserted validation evidence. An inaccessible/invalid P cannot be retained merely because its ID was named. Cancel/retain closes the N attempt immediately; no durable failure can reopen it. Session-only abandons N's **storage** attempt but preserves the still-current pending in-memory authorization only for a separate explicit activation request.

| Public operation / private event | Ordered action, acknowledgement and crash result |
| --- | --- |
| `attempt(..., Stage)` | Revalidate authorized live attempt and distinct N/P. Atomically commit the intent, conservatively dispatched marker and account `Unresolved` **before** provider I/O. Failure dispatches nothing. Create exact N, never update P. `Staged` reports the actual committed record and independent settlement, not persistence success. |
| Private provider settlement | Record definitive writer completion and exact presence/non-write while preserving the selected disposition. Timeout/lost reply remains unknown even if a lookup currently says absent. A late callback cannot call activation. Crash before recording settlement leaves uncertainty. |
| `attempt(..., ActivateStored)` | Revalidate current noncancelled attempt, canonical identity, explicit persistence intent and settled confirmed accessible N. Commit `Eligible(N)` and activation before issuing a fresh runtime. A receipt alone never authorizes a stale callback. Retiring P is separate authorized work. |
| `maintain(..., Abandon(SessionOnly))` | Atomically abandon N's store, create its exact cleanup marker and commit account-wide `Suppressed`, covering N, P and any older generation. No runtime activation occurs. The result is `MaintenanceOutcome::Abandoned` with the exact choice, committed account/revision/disposition and independent settlement. This also works without a dispatched write; record a known non-write only when proved. |
| `attempt(..., ActivateSessionOnly(receipt))` | Optional separate memory activation. `SessionOnlyCommit::from_acknowledgement(context, expected, report)` requires the exact explicit session-only request, transition ID and committed account-wide suppression; settlement or a plain suppression report cannot create it. The owner then rechecks the **latest** committed revision/disposition, selected choice, validated current attempt, cancellation/deadline and canonical identity before issuing a runtime. Unknown N shows `SessionOnlyCleanupPending`; confirmed non-write/settled absence permits `SessionOnly`. P stays untouched and ineligible. |
| `maintain(..., Abandon(Cancel))` | Locally invalidate the attempt immediately, discard pending secrets, atomically mark exact-N cleanup and suppress all generations. Do not guess that P should restore. No prior session means unconnected. A still-valid prior in-memory session may remain only according to its existing admission; this command grants no persistence to it. |
| `maintain(..., Abandon(RetainPrevious { ... }))` | Locally invalidate N immediately. Revalidate deliberately named P through the stated basis, then atomically commit its sole `Eligible(P)` disposition and exact-N abandonment/cleanup marker. Cleanup uncertainty does not invalidate that committed retention. This method never issues a runtime; cold recovery uses `restore` later. Failed commit preserves the last committed disposition (including unresolved suppression), with an honest warning. |
| `maintain(..., Suppress(cause))` | After local account rejection/logout/removal closure, commit account-wide suppression under separate supervisor authority. `AccountRejected(scope)` and `Logout(scope)` carry the closed scope as correlation, not authorization; `AccountRemoval` uses the supervisor's account. Record all affected outstanding attempts as closed/abandoned and retain exact-N cleanup obligations. No old callback can activate. This does not authorize blanket deletion of P or other accounts' items. |
| `maintain(..., Reconcile(intent))` | Resolve writer settlement and exact item presence separately; preserve the current selected disposition. Reconcile the same writer before retrying a save. `MaintenanceOutcome::Reconciled` cannot become a session-only activation receipt, even for `SettledPresent`. |
| `maintain(..., DeleteAbandonedAttempt(intent))` | Require the ledger's exact-N abandonment marker and no-writer settlement before deletion. Confirm absence and commit cleanup completion, idempotently. A caller-supplied descriptor alone does not authorize deletion. `CleanupMarker::complete` is necessary but final success also needs that durable completion. Never wildcard-delete or treat P as collateral. |

`CommittedRestoration { account, revision, disposition }` is an owner-reported **durable acknowledgement or intact committed-record load**, distinct from `Abandonment::requested_disposition` and `Settlement`. Its public fields permit fault-injected contract tests, not a fabricated storage proof. `IdentityStatus.restoration = None` means no confirmed record, never implicit suppression. `MaintenanceReport::acknowledges_abandonment` checks exact account/transition/request/disposition correlation for all three choices. `SessionOnlyCommit` has private fields and can only be obtained from that explicit session-only acknowledgement; it remains a receipt with necessary predicates, not a capability. The owner must reject its stale revision or superseded choice even if its local matching predicate passes. Metadata failure returns an error/no new committed acknowledgement; never echo requested suppression as success or relabel provider completion as durable activation.

All methods perform bounded nonblocking admission **when called**, before returning their observation task. The accepted operation and provider ledger belong to the supervisor, not to that task. Dropping/cancelling an unfinished attempt/recovery observer closes its activation authority; it cannot discard a previously dispatched write or its settlement/cleanup obligation. A drop racing an already committed activation must be serialized: if drop wins, no activation; if activation won, immediately close that undelivered runtime and retain durable cleanup/suppression work as required, never continue invisible authenticated activity. Dropping an already consumed successful observation does not undo its completed handoff. Dropping a maintenance observer affects delivery only. Returning `Busy` before admission promises no new provider write; local cancellation and priority account suppression still proceed independently.

Suppression is a ledger operation and must not wait for a hung provider writer or exhausted ordinary provider capacity. Serialize metadata decisions, not a blocking wait on the provider; retain the independent uncertain-writer record while committing a restrictive choice.

The supervisor has 8 descriptors/account (7 ordinary plus 1 reserved coalesced suppression slot), one provider operation/account and two provider workers globally, as in ADR-002. A maintenance slice expires after 3 s or a clock-epoch change; renew only under a bounded user/provider/startup recovery trigger, with no prompt/retry loop. This is a dispatch/observation deadline, **not** a promise that a native write stops in 3 s. An uncertain writer keeps its bounded slot and nonsecret ledger record; do not spawn replacements until settlement. Root shutdown attempts a bounded ledger flush/worker join, retains committed unresolved records and reports any failed durable suppression. Process death, dropping a task or killing a worker proves no settlement. The supervisor/queues/drop handling are specified, not implemented by the context types.

macOS Keychain item APIs provide item results; **no durable operation-ID/settlement query is assumed**. A synchronous worker return can supply settlement while the process lives. If the process dies during an OS write, item lookup alone is insufficient to prove no late writer can recreate it. Until a platform-qualified recovery barrier establishes settlement, keep the cleanup marker and warning, preserve `P`, never restore abandoned `N` and require explicit recovery. Unresolved/suppressed account state blocks automatic restoration of every generation; the sole exception is an already committed deliberate cancel-and-retain decision, which permits only its named valid `P` while `N` cleanup remains pending (AUTH-005 / V.AUTH.STORE-03). A committed session-only disposition still suppresses all generations; settlement/cleanup can never turn it into eligibility. Killing a worker or observing early absence is not that barrier. Automatic replacement/cleanup on such a path stays unsupported if qualification cannot establish it. This limitation affects availability, not the suppression rule; do not invent a Keychain transaction API.

If durable suppression cannot commit, do **not** activate a replacement under a session-only promise. Offer repair/retry or cancel-and-retain; cancellation still invalidates the attempt locally. If a secret cannot be read, session-only requires fresh authorization or a valid existing in-memory session. No cancelled/failed write may trigger a later automatic save. An explicit save uses a new generation after prior reconciliation. Once a session-only runtime has activated, provider recovery or retention of the old completed attempt cannot re-enable persistence; it needs that new explicit confirmed save.

Required provider categories are `Missing`, `Locked`, `AccessDenied`, `Corrupt`, `TemporarilyUnavailable`, `Unavailable`, `Unsupported`, `Cancelled`, `Other`, with operation/provider/account/retry/native-code metadata. Interpret native codes according to primary documentation: disallowed interaction is not proof of a locked vault. The UI gets a stable category and exact residual-state wording from AUTH-004, never raw native error descriptions or a wrong-password conclusion derived from vault failure.

## Account rejection classifier and fan-out

For both supported server families, the authoritative account probe is same-origin **`GET /ocs/v2.php/cloud/user?format=json`**, using only the intended app password, no ambient browser cookies and no redirects. The pinned route maps to `Users#getCurrentUser`. An OCS v2 unauthorized result uses OCS status **997** and HTTP **401** in the inspected response/middleware path. Sources for both releases are linked in [A-SRC-04](../source-evidence.md#a-src-04--account-probe).

`ConfirmedAccountProbe` requires an uncached, TLS-authenticated response from the configured canonical installation, a complete well-formed OCS failure envelope with that unauthorized status, the same still-current runtime scope, and a qualified endpoint mapping. A successful probe must return the expected canonical user ID. A changed ID closes admission as an identity mismatch and requires explicit repair; it cannot inherit the account's pending work. This confirms unusable authorization for the selected account, not its cause (revocation, deletion, admin action, etc.). Proxy HTML, missing OCS metadata, generic 401/403, TLS failures, captive portals and contradictory responses remain ambiguous. No success from the public capabilities endpoint proves account authorization.

| Evidence | Action |
| --- | --- |
| Confirmed account-probe rejection | Account-wide shutdown, below |
| Forbidden room operation, no `START_CALL`, lobby/room removal | Restrict/reconcile that action or room; no credential deletion or other-account invalidation |
| HPB ticket/session expiry or internal room session loss | Close affected call admission, reconcile session; not account rejection by itself |
| Timeout/DNS/5xx/rate limit/malformed/ambiguous authorization response | Mark degraded, schedule one bounded probe; retain credentials. In-flight media follows its independent policy expiry. |

The probe is coalesced with ADR-004's active-call refresh. Outside calls, an ambiguous action triggers at most one probe at a time with a 3 s deadline, then 2/4/8/16/30 s bounded jittered retry (maximum 30 s, respecting longer server retry guidance). No endless immediate login/prompt/retry loop. Failed probes never renew media authority. Exact unauthorized envelopes and successful identity binding must be live-tested on both releases before enabling this classifier; an unqualified form remains ambiguous.

At confirmed observation `t0`, the account actor synchronously closes authenticated admission and permanently invalidates the runtime. It broadcasts the same cancellation token to owned requests, transfers, sends, background/signaling work and rejects old login/policy/media completions. It closes the media publication gate in the same transition, then invokes priority stop independently of account cancellation. Publication/queue closure must complete by `t0 + 250 ms`; capture/device release by **`t0 + 1,000 ms`**, with watchdog/failure semantics in [ADR-004](004-policy-media-lifecycle.md#local-enforcement-and-failure). Remote leave/revocation, vault cleanup and metadata I/O cannot delay these local actions.

In parallel, the identity supervisor calls `maintain` with `Suppress(AccountRejected(closed_scope))` under its own `MaintenanceContext`, committing account-wide restoration suppression including older items. It closes all previously outstanding attempt IDs for this account; new login requires a new deliberate attempt. The invalidated runtime token cannot cancel this maintenance, and delayed retain/activate requests cannot reopen the closed scope. If persistence fails, runtime shutdown remains complete and the UI states restart suppression is unconfirmed. Permitted drafts and other accounts survive. Already sent data cannot be recalled; uncertain sends remain delivery-unknown. New validated authorization gets a new runtime and fresh gates, then requires deliberate send retry or rejoin. It cannot replay work, unmute, start a camera or resume sharing automatically.

Acceptance: all V.AUTH.STORE-01–06 and V.AUTH.LOSS-01–03, crash injection before/after each durable/provider boundary, two users/installations/profiles, failed suppression, late callbacks, provider lock/denial/signing changes and actual capture stop. Bootstrap tests substantiate only cleanup/admission/correlation algebra and the ability to call the unconfigured seams without fabricated runtimes. They do not execute a supervisor, ledger commit, native provider, drop race or crash recovery. The [remediation report](../../reviews/bootstrap-remediation-r1.md) records preliminary execution; independent rechecks and native proof remain pending.
