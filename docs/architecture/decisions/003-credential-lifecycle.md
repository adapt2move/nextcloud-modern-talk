# ADR-003 — Identity, durable restoration and account loss

Status: architecture contract for [AMEND-AUTH-STORAGE-01](../../product/accounts.md#spec-amendment--amend-auth-storage-01) and [ADR-006](006-credential-providers.md). AUTH-003–008, Q.SEC-02–05 and V.AUTH.STORE/LOSS remain normative. Credentials and I/O stay adapter-private. The current identity correction draft is stopped and unverified; this document supplies no runtime or platform pass.

## Identities and authority

The identity adapter owns browser authorization, pending secrets, native/file provider selection and storage/metadata transactions. It serializes transitions per account; the application account actor owns authenticated admission. A profile-wide single-writer process lock plus transactional revision comparison must prevent two processes from replacing the same account independently, including through different backends. Losing that lock closes admission for restoration mutations, never silently becomes a second writer. The I2 private profile lock, SQLite transactions and checked revision comparisons implement these mechanisms; hardware power-loss behavior remains a platform qualification item.

| Identity | Meaning and invalidation |
| --- | --- |
| `AccountId`, `ProfileId`, `HostId` | Random local IDs; persisted private account-metadata binding to canonical server base URL including installation path and canonical server user ID. Login name is stored separately from canonical identity. Two users or installations never share a key. |
| `RuntimeGeneration` | Validated in-memory authorization lifetime. Logout, replacement activation or confirmed account rejection permanently closes it. It is not a vault generation or a persisted reusable token. |
| `LoginAttemptId` | One pending browser flow/replacement attempt. Cancellation abandons this attempt without implicitly invalidating a deliberately retained valid older runtime. |
| `VaultGeneration`, `OperationId` | Immutable generation and writer-operation IDs; the existing generation name covers native **and file** items. A generation is interpreted only with its qualified backend/account binding. New attempts never overwrite old generations; timeout/cancellation is not settlement. |
| `ProviderBinding`, `QualifiedItem` (bounded core orchestration records) | Backend kind + local OS-user/profile store scope + stable configuration/store binding, then account/secret-kind/schema/generation. `N` and `P` each carry their own binding; equal numeric generations in different providers are never interchangeable. |
| `CallGeneration` | One local join/incoming acceptance lifecycle; account scope and conversation-host scope are embedded. Reauthorization cannot reactivate it. |

Item identity is application namespace `org.adapt2move.nextcloud-modern-talk` + profile + account + qualified backend binding + secret kind + schema version + generation. Selected backend kinds are `macos-keychain-user-v1`, `windows-credential-local-v1`, `linux-secret-service-v1`, and `private-file-v1`. Labels/paths contain no secret or raw user/server path components. Native routing uses ADR-006's exact crate selection: User/login Keychain; user-scoped Credential Manager with local persistence; qualified Linux Secret Service and collection. File routing uses an independently validated private per-user directory. Session-only is a mode, not a file or native backend.

The registry stores the stable configuration and private native store/collection or local file-root binding needed to address the same provider after restart. Validate the actual OS-user/store scope against that record. A crate's generated process-instance `id()` or the currently available default provider is not this binding. Changed/missing/unverifiable bindings require recovery; never guess a replacement collection, directory or OS provider. No native daemon UUID or portable ACL/settlement API is assumed. Native synchronization/access/signing properties and file root ownership/ACLs still require qualification under [Q.SEC-03/04](../../quality/security.md#qsec-03--os-vault-contract).

A fresh account reserves its random local account/attempt/N/provider-operation IDs against a validated server binding before browser login. Canonical user binding is established by identity validation, not by reserving these IDs. `RuntimeGeneration` is issued only after validated activation/restoration; it is never invented for this reservation.

Only adapter-private code can materialize an app password or guest/signaling token. Authenticated worker operations use `AccountScope`; pending authorization, recovery and maintenance have separate contexts; the identity owner lends the secret directly to a validated, origin-bound transport operation and releases its temporary buffer. Core, UI, diagnostics, task descriptors and media control receive no secret. Native persistence, **unencrypted private-file persistence** and optional session-only are explicit modes under AUTH-003–005. No primary password, token environment variable, clipboard, log, shared cache, adjacent-key encryption or mock store substitutes for the selected backend. This amendment does not persist transient guest/signaling secrets or redesign content caching.

## Private restoration-metadata durability decision

Use a separate **SQLite restoration ledger** with a single writer, rollback journal `DELETE`, `synchronous=EXTRA`, and macOS `fullfsync=ON`, subject to native filesystem/power-loss qualification. I2 links pinned rusqlite 0.40.2 with bundled SQLite and verifies effective settings. The selected build/VFS and OS still require hardware crash/power-loss qualification; unsupported flush guarantees leave restoration unqualified. The decision uses SQLite's [atomic commit model](https://www.sqlite.org/atomiccommit.html) and [documented pragmas](https://www.sqlite.org/pragma.html#pragma_synchronous), not a claim that writes are already durable on arbitrary hardware.

The original amendment described **logical schema version 2**. I2 implements **private SQLite schema 5**, retaining those logical decisions while adding exact login-name metadata, bounded operation failure categories and checked full-width ID/revision encoding. Earlier I2 schemas were unreleased author inputs; there is no automatic migration or deployed database conversion. The following logical records are updated transactionally; the runtime contract specifies actual limits. If an older/unknown/incomplete ledger is encountered later, require explicit validated recovery; do not infer backend or eligibility from available items.

- `AccountRestoration`: profile/account/origin/user binding, monotonic revision, committed mode (`SessionOnly` or `Persistent(ProviderBinding)`), disposition (`Suppressed`, `Unresolved`, or `Eligible(QualifiedItem)`), exact retained `P` and active attempt if any. Mode alone is not eligibility. A persistent mode names only one restoration backend.
- `StoreOperation`: operation/attempt IDs, requested destination/mode and explicit save/migration authority, qualified attempted `N` and retained `P`, phase (`IntentCommitted`, `Dispatched`, `SettledPresent`, `SettledAbsent`, `Abandoned`, `Activated`), settlement evidence and nonsecret error category. Pending destination choice is committed before dispatch; it does not replace committed restoration mode until activation. Abandonment and writer settlement remain independent fields.
- `CleanupMarker`: exact account/backend/attempted item and staging identity, reason, pending settlement/deletion state and last allowlisted provider code. Retiring `P` requires a separate explicitly authorized operation, even when P and N use different providers.

The ledger, its journal and its backups contain **no app password or primary password**. Exact login identifiers and expected canonical IDs are private account metadata, never public data or diagnostics. They do contain sensitive account metadata: restrict filesystem access and exclude them from public diagnostics. Secret-bearing files belong only to the separately selected private-file provider, never a ledger/error-recovery export. Each commit compares the expected revision, completes its durable transaction and only then acknowledges the transition. Missing/corrupt/inconsistent metadata is `RecoveryRequired`; native/file enumeration cannot reconstruct eligibility. Deleting the ledger cannot make a surviving credential restorable. Validate schema, choice and complete binding before resolution.

## Operations and crash ordering

The historical `IdentityPort` trait retains four worker methods plus availability;
`UnconfiguredIdentity` still honestly returns Unconfigured. It is not the implemented
desktop entrypoint. I2's cohesive `IdentityRuntime` owns the registry, providers,
account clients and bounded command/observation lifetime described in the
[runtime contract](../identity-contract.md). It implements the ordering decisions
below through separate Begin/Poll/Save, Restore/ResolvePrevious and
StorageStatus/Retire/Maintain operations; it does not expose credentials through
the bootstrap trait. The table preserves that historical logical vocabulary for
review. N and P mean fully backend-qualified items, never bare generations.

| Signature | Authority and permitted result |
| --- | --- |
| `attempt(PendingAttemptContext, AttemptCommand) -> Task<AttemptReport>` | `PendingAttemptContext { intent: StoreIntent, deadline, cancellation }` carries account/attempt/N/P/provider-operation identity, **no runtime**. `Authorize` starts/continues a bounded system-browser flow and validates the intended canonical identity without activating it. `Stage`, `ActivateStored` and `ActivateSessionOnly(SessionOnlyCommit)` operate on that same current attempt. `AttemptReport` distinguishes `Authorized`, `Staged` and `Activated`; only explicit activation after revalidation issues a fresh runtime. |
| `restore(RecoveryContext) -> Task<RestoredIdentity>` | `RecoveryContext { account, operation, deadline, cancellation }` requires no live runtime. Load intact committed metadata, select only its exact eligible generation, resolve/validate that item privately against the intended canonical account, then issue a fresh runtime. Missing/corrupt/unresolved/suppressed metadata cannot restore by enumeration. `RestoredIdentity` correlates the recovery operation, account/runtime, exact item and committed record. |
| `resolve(OperationContext) -> Task<IdentityStatus>` | Requires a still-admitted authenticated scope before dispatch and result delivery. Private credential borrowing is limited to a validated origin-bound transport operation; this method returns only redacted state, never a reusable secret/auth object. |
| `maintain(MaintenanceContext, MaintenanceCommand) -> Task<MaintenanceReport>` | The identity supervisor alone supplies `MaintenanceContext::for_supervisor(account, operation, now)`, with a finite 3 s slice and **no runtime or caller cancellation token**. Commands are `Abandon(Abandonment)`, `Suppress(SuppressionCause)`, `Reconcile(StoreIntent)` and `DeleteAbandonedAttempt(StoreIntent)`. Results contain only correlated committed restoration/settlement/cleanup observations, never an activated runtime. Referencing a rejected runtime identifies the loss being settled; it does not grant authenticated authority. |

`StoreIntent.operation` always identifies the original provider writer; `MaintenanceContext.operation` identifies the separate maintenance transition. Reuse a transition ID only to observe/retry that exact semantic decision; a new choice uses a new ID. Every command must validate account/attempt/**both backend bindings**/N/P/writer and selected mode against the registry/ledger before effects; every durable mutation serializes against the current account revision. A stale transition cannot overwrite a newer suppression/retention/activation, and another account's descriptors cannot affect this one. Current `MaintenanceCommand::is_scoped_to`, `PendingAttemptContext::admits` and acknowledgement predicates check only their named correlations/time bounds, not a registry, provider or database. The implemented runtime therefore checks its private ledger and current revision separately; those predicates are never sufficient authority by themselves.

`Abandonment::new(intent, choice)` rejects `N == P`, retention of a generation other than the named P, and a retained runtime from a different account. Choices are explicit: `SessionOnly`, `Cancel`, or `RetainPrevious { generation, validation }`. `RetentionValidation::CurrentRuntime(scope)` must still be admitted, bound to P and canonically valid at commit; `RevalidateStored` is an explicit cold-recovery request to validate that exact stored P privately, not asserted validation evidence. An inaccessible/invalid P cannot be retained merely because its ID was named. Cancel/retain closes the N attempt immediately; no durable failure can reopen it. Session-only abandons N's **storage** attempt but preserves the still-current pending in-memory authorization only for a separate explicit activation request.

| Public operation / private event | Ordered action, acknowledgement and crash result |
| --- | --- |
| `attempt(..., Stage)` | Revalidate authorized live attempt and distinct N/P. Atomically commit the intent, conservatively dispatched marker and account `Unresolved` **before** provider I/O. Failure dispatches nothing. Create exact N, never update P. `Staged` reports the actual committed record and independent settlement, not persistence success. |
| Explicit file choice / later save or migration | Reconcile any prior writer first; commit a new operation/attempt and fresh target N with its requested backend. Source the app credential only from validated live memory or an explicitly read/revalidated selected P; otherwise require fresh browser authorization. Keep pending destination choice separate from committed restoration mode. Use the same Stage/ActivateStored ordering, not a special fallback bypass. |
| Private provider settlement | Record definitive writer completion and exact presence/non-write while preserving the selected disposition. Timeout/lost reply remains unknown even if a lookup currently says absent. A late callback cannot call activation. Crash before recording settlement leaves uncertainty. |
| `attempt(..., ActivateStored)` | Revalidate current noncancelled attempt, canonical identity, target backend/choice and settled confirmed accessible N (including file access/durability checks). Atomically commit the selected persistent mode and sole `Eligible(N)` before success/activation. A receipt alone never authorizes a stale callback. Retiring P is separate authorized work. Migration itself never replays authenticated work or grants a new call. |
| `maintain(..., Abandon(SessionOnly))` | Atomically abandon N's store, create its exact cleanup marker and commit `SessionOnly` mode plus account-wide `Suppressed`, covering N, P and all older generations/backends. No runtime activation occurs. The result is `MaintenanceOutcome::Abandoned` with the exact choice, committed account/revision/disposition and independent settlement. This also works without a dispatched write; record a known non-write only when proved. |
| `attempt(..., ActivateSessionOnly(receipt))` | Optional separate memory activation. `SessionOnlyCommit::from_acknowledgement(context, expected, report)` requires the exact explicit session-only request, transition ID and committed account-wide suppression; settlement or a plain suppression report cannot create it. The owner then rechecks the **latest** committed revision/disposition, selected choice, validated current attempt, cancellation/deadline and canonical identity before issuing a runtime. Unknown N shows `SessionOnlyCleanupPending`; confirmed non-write/settled absence permits `SessionOnly`. P stays untouched and ineligible. |
| `maintain(..., Abandon(Cancel))` | Locally invalidate the attempt immediately, discard pending secrets, atomically mark exact-N cleanup and suppress all generations. Do not guess that P should restore. No prior session means unconnected. A still-valid prior in-memory session may remain only according to its existing admission; this command grants no persistence to it. |
| `maintain(..., Abandon(RetainPrevious { ... }))` | Locally invalidate N immediately. Revalidate deliberately named P through the stated basis, then atomically commit P's persistent backend/mode, sole `Eligible(P)` and exact-N abandonment/cleanup marker. Cleanup uncertainty does not invalidate that committed retention. This method never issues a runtime; cold recovery uses `restore` later. Failed commit preserves the last committed disposition (including unresolved suppression), with an honest warning. |
| `maintain(..., Suppress(cause))` | After local account rejection/logout/removal closure, commit account-wide suppression under separate supervisor authority. `AccountRejected(scope)` and `Logout(scope)` carry the closed scope as correlation, not authorization; `AccountRemoval` uses the supervisor's account. Record all affected outstanding attempts as closed/abandoned and retain exact-N cleanup obligations. No old callback can activate. This does not authorize blanket deletion of P or other accounts' items. |
| `maintain(..., Reconcile(intent))` | Resolve writer settlement and exact item presence separately; preserve the current selected disposition. Reconcile the same writer before retrying a save. `MaintenanceOutcome::Reconciled` cannot become a session-only activation receipt, even for `SettledPresent`. |
| `maintain(..., DeleteAbandonedAttempt(intent))` | Require the ledger's exact-N abandonment marker and no-writer settlement before deletion. Confirm absence and commit cleanup completion, idempotently. A caller-supplied descriptor alone does not authorize deletion. `CleanupMarker::complete` is necessary but final success also needs that durable completion. Never wildcard-delete or treat P as collateral. |
| Restart / OS-store recovery | Resolve only the backend/item named by the current eligible record and validate the canonical account. A valid file item remains the choice even when Keychain/Credential Manager/Secret Service becomes available. Session-only remains suppressed. No backend enumeration, implicit migration, generation merge, automatic source retirement or abandoned-N activation. |

`CommittedRestoration { account, revision, disposition }` is an owner-reported **durable acknowledgement or intact committed-record load**, distinct from `Abandonment::requested_disposition` and `Settlement`. Its public fields permit fault-injected contract tests, not a fabricated storage proof. `IdentityStatus.restoration = None` means no confirmed record, never implicit suppression. `MaintenanceReport::acknowledges_abandonment` checks exact account/transition/request/disposition correlation for all three choices. `SessionOnlyCommit` has private fields and can only be obtained from that explicit session-only acknowledgement; it remains a receipt with necessary predicates, not a capability. The owner must reject its stale revision or superseded choice even if its local matching predicate passes. Metadata failure returns an error/no new committed acknowledgement; never echo requested suppression as success or relabel provider completion as durable activation. The implemented supervisor retains a failed restrictive decision in a per-account admission latch until its exact commit succeeds. Maintain/RetireAll may retry once per admitted command; read-only status or empty cleanup cannot clear it. Published revisions come from committed metadata. Same-process restore of old eligible P stays blocked; persistence failure still means restart suppression is unconfirmed.

All methods perform bounded nonblocking admission **when called**, before returning their observation task. The accepted operation and provider ledger belong to the supervisor, not to that task. Dropping/cancelling an unfinished attempt/recovery observer closes its activation authority; it cannot discard a previously dispatched write or its settlement/cleanup obligation. A drop racing an already committed activation must be serialized: if drop wins, no activation; if activation won, immediately close that undelivered runtime and retain durable cleanup/suppression work as required, never continue invisible authenticated activity. An Authorized Poll enqueued but unread still carries its attempt-scoped cancellation guard; dropping it revokes exactly that grant, without changing retained P when no N was staged. Dropping an already consumed successful observation does not undo its completed handoff. Dropping a maintenance observer affects delivery only. Returning `Busy` before admission promises no new provider write; local cancellation and priority account suppression still proceed independently.

Suppression is a ledger operation and must not wait for a hung provider writer or exhausted ordinary provider capacity. Serialize metadata decisions, not a blocking wait on the provider; retain the independent uncertain-writer record while committing a restrictive choice.

The implementation releases the UI-facing pending-attempt mutex before its synchronous suppression commit, after transferring the exact cancelled attempt to the owner. A test-only disk barrier verifies an external composition thread can signal cancellation/logout and close local use before that barrier is released. The restrictive decision is installed before the fallible acknowledgement. This proves the local lock boundary; it does not qualify all synchronous ledger/worker I/O latency.

The supervisor has 8 descriptors/account (7 ordinary plus 1 reserved coalesced suppression slot), one provider operation/account and two provider workers globally, as in ADR-002. A maintenance slice expires after 3 s or a clock-epoch change; renew only under a bounded user/provider/startup recovery trigger, with no prompt/retry loop. This is a dispatch/observation deadline, **not** a promise that a native write stops in 3 s. An uncertain writer keeps its bounded slot and nonsecret ledger record; do not spawn replacements until settlement. Root shutdown attempts a bounded ledger flush/worker join, retains committed unresolved records and reports any failed durable suppression. Process death, dropping a task or killing a worker proves no settlement. The runtime and supervisor implement queue/drop ownership; the context types only carry scope and cancellation. Their native/platform limits are recorded in the identity integration contract.

The selected native crates provide item results; **no durable operation-ID/settlement query is assumed**. A synchronous worker return can supply settlement while the process lives. If the process dies during an OS write, lookup alone cannot prove no late writer can recreate it. The file provider also owes a qualified exclusive recovery barrier covering its owned writers, pending OS I/O and durable installation; a newly acquired lock or absent pathname alone is not that proof. Until settlement is established, retain the marker/warning and bounded worker accounting, preserve `P`, never restore abandoned `N` and require explicit recovery. Selecting file mode cannot free an uncertain native-writer slot or evade this barrier.

Unresolved/suppressed account state blocks restoration of every generation/backend; the sole exception is an already committed deliberate cancel-and-retain decision, permitting only named valid `P` while `N` cleanup remains pending (AUTH-005 / V.AUTH.STORE-03). Session-only suppresses all generations; settlement/cleanup cannot turn it into eligibility. Killing a worker or observing early absence is not the barrier. Automatic replacement/cleanup remains unsupported where qualification cannot establish it. This limitation concerns uncertain operations, not ordinary no-provider startup: a **known non-write** permits a new explicit file save and durable file restoration thereafter. Do not invent a native transaction API.

If durable suppression cannot commit, do **not** activate a replacement under a session-only promise. Offer repair/retry or cancel-and-retain; cancellation still invalidates the attempt locally. If a secret cannot be read, session-only requires fresh authorization or a valid existing in-memory session. No cancelled/failed write may trigger a later automatic save. An explicit save uses a new generation after prior reconciliation. Once a session-only runtime has activated, provider recovery or retention of the old completed attempt cannot re-enable persistence; it needs that new explicit confirmed save.

Required provider categories are `Missing`, `Locked`, `AccessDenied`, `Corrupt`, `TemporarilyUnavailable`, `Unavailable`, `Unsupported`, `Cancelled`, `Other`, with operation/qualified-provider/account/retry/allowlisted-code metadata. Interpret codes through [ADR-006's source-bound mapper](006-credential-providers.md#api-and-error-boundary): disallowed interaction is not proof of a locked vault; missing service is not missing item. The UI gets a stable category, actual file/native/session mode and AUTH-004's residual-state wording, never raw errors or a wrong-password conclusion derived from storage failure.

The file provider's owner/permission/DACL/path checks, immutable-generation atomic installation, bounds, crash/corruption handling and repair rules are [Q.SEC-04](../../quality/security.md#private-file-provider). No bespoke crypto or secret-bearing recovery file is involved. A failed save/migration keeps the last committed disposition and `P`; if intent already committed it normally remains `Unresolved`, not implicitly eligible P. Only committed deliberate retention can restore P. Failure to retire an explicitly replaced source after successful target activation leaves sole target eligibility plus a visible source-cleanup marker; it never rolls back by selecting an arbitrary surviving item.

## Account rejection classifier and fan-out

For both supported server families, the authoritative account probe is same-origin **`GET /ocs/v2.php/cloud/user?format=json`**, using only the intended app password, no ambient browser cookies and no redirects. The pinned route maps to `Users#getCurrentUser`. An OCS v2 unauthorized result uses OCS status **997** and HTTP **401** in the inspected response/middleware path. Sources for both releases are linked in [A-SRC-04](../source-evidence.md#a-src-04--account-probe).

`ConfirmedAccountProbe` requires an uncached, TLS-authenticated response from the configured canonical installation, a complete well-formed OCS failure envelope with that unauthorized status, the same still-current runtime scope, and a qualified endpoint mapping. A successful probe must return the expected canonical user ID. A changed ID closes admission as an identity mismatch and requires explicit repair; it cannot inherit the account's pending work. This confirms unusable authorization for the selected account, not its cause (revocation, deletion, admin action, etc.). Proxy HTML, missing OCS metadata, generic 401/403, TLS failures, captive portals and contradictory responses remain ambiguous. No success from the public capabilities endpoint proves account authorization.

| Evidence | Action |
| --- | --- |
| Confirmed account-probe rejection | Account-wide shutdown, below |
| Forbidden room operation, no `START_CALL`, lobby/room removal | Restrict/reconcile that action or room; no credential deletion or other-account invalidation |
| HPB ticket/session expiry or internal room session loss | Close affected call admission, reconcile session; not account rejection by itself |
| Timeout/DNS/5xx/rate limit/malformed/ambiguous authorization response | Mark degraded, schedule one bounded probe; retain credentials. In-flight media follows its independent policy expiry. |

The probe is coalesced with ADR-004's active-call refresh. Outside calls, an ambiguous action triggers at most one probe at a time with a 3 s deadline, then 2/4/8/16/30 s bounded jittered retry (maximum 30 s, respecting longer server retry guidance). No endless immediate login/prompt/retry loop. Failed probes never renew media authority. Exact unauthorized envelopes and successful identity binding must be live-tested on both releases before enabling this classifier; an unqualified form remains ambiguous.

At confirmed observation `t0`, the account actor synchronously closes authenticated admission and permanently invalidates the runtime. It broadcasts the same cancellation token to owned requests, transfers, sends, background/signaling work and rejects old login/policy/media completions. It closes the media publication gate in the same transition, then invokes priority stop independently of account cancellation. Publication/queue closure must complete by `t0 + 250 ms`; capture/device release by **`t0 + 1,000 ms`**, with watchdog/failure semantics in [ADR-004](004-policy-media-lifecycle.md#local-enforcement-and-failure). Remote leave/revocation, vault cleanup and metadata I/O cannot delay these local actions.

In parallel, the identity supervisor calls `maintain` with `Suppress(AccountRejected(closed_scope))` under its own `MaintenanceContext`, committing account-wide restoration suppression including older items. It closes all previously outstanding attempt IDs for this account; new login requires a new deliberate attempt. The invalidated runtime token cannot cancel this maintenance, and delayed retain/activate requests cannot reopen the closed scope. If persistence fails, runtime shutdown remains complete and the UI states restart suppression is unconfirmed. Permitted drafts and other accounts survive. Already sent data cannot be recalled; uncertain sends remain delivery-unknown. New validated authorization gets a new runtime and fresh gates, then requires deliberate send retry or rejoin. It cannot replay work, unmute, start a camera or resume sharing automatically.

Acceptance: V.AUTH.STORE-01–16 and V.AUTH.LOSS-01–03, both native/file sources and targets, every durable/provider crash boundary, two users/installations/profiles, unsafe permissions/ACLs, no-service startup, failed suppression, late callbacks, lock/denial/signing changes and actual capture stop when media exists.
