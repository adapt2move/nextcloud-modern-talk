# ADR-006 — Credential providers and durable file fallback

Status: selected provider and storage contract for [AMEND-AUTH-STORAGE-01](../../product/accounts.md#spec-amendment--amend-auth-storage-01). The current identity correction draft is stopped and unverified; native macOS/Windows qualification remains pending. [ADR-003](003-credential-lifecycle.md) owns lifecycle/ledger semantics and [Q.SEC-03/04](../../quality/security.md#qsec-03--os-vault-contract) owns protection requirements.

## Decision and scope

Use maintained **explicit native provider crates** inside the existing identity adapter: keyring-core providers on macOS/Windows and the typed prompt-disabled dbus-secret-service API on Linux. The user asked for a ready-made Rust OS-store abstraction, durable persistence when that store is unavailable, and **“Keine verschlüsselung”** for the file fallback. Native stores retain their own OS protection. The fallback is a dedicated unencrypted private file, with no master password, KDF, application encryption, embedded key or additional approval workflow. Optional session-only operation is preserved.

The currently published [`keyring 4.2.0` guidance](https://github.com/open-source-cooperative/keyring-rs/blob/d18b5c89a0a4e9192eebac82a508a1607378ea15/src/lib.rs) directs applications needing store control to `keyring-core` and chosen provider crates. Its `v1` convenience mode and broad `cli` feature set are not selected. Do not copy the CLI/sample implementation, use `keyring-core::sample` as the production file store, or use mock/Linux keyutils storage as durable fallback. The core's own [README](https://github.com/open-source-cooperative/keyring-core/blob/50fe5c44fa3dc46cdf792acfe5116e1e8ebc2e0b/README.md) describes the sample and mock stores as unsuitable for production.

The Linux path uses a DH-protected native service session with `crypto-rust`; this **does not encrypt the fallback file**. Typed item/collection methods must avoid automatic unlock, and zero prompt timeout must refuse returned prompts; an advisory unlocked preflight alone cannot exclude a later lock race. See [item methods](https://github.com/brotskydotcom/dbus-secret-service/blob/d739c219802a213746dfcd6358c46723c3fc42e3/src/item.rs), [collection methods](https://github.com/brotskydotcom/dbus-secret-service/blob/d739c219802a213746dfcd6358c46723c3fc42e3/src/collection.rs), and [prompt guard](https://github.com/brotskydotcom/dbus-secret-service/blob/d739c219802a213746dfcd6358c46723c3fc42e3/src/prompt.rs). The adapter never calls Unlock/ensure_unlocked, even with that guard enabled.

The existing `secret-service =5.2.0` and `zbus =5.19.0` edges retain typed connection/absence classification in the advisory preflight. `zbus-secret-service-keyring-store =1.0.1` remains pinned for the cfg(test)-only legacy-record writer proving existing P compatibility; production operations never select it. Its retained target dependency has a compilation cost and is not a fallback provider. No other existing registry entry changes. The three added registry packages are dbus-secret-service4.1.0, dbus0.9.12 and libdbus-sys0.2.7, all offering MIT/Apache-2.0; source/license hashes are in the manifest. Select MIT for those Rust crates and preserve notices. The observed system libdbus1.16.2 has separate native-library licensing and packaging obligations (GPL-2.0-or-later OR AFL-2.1, with component notices); [upstream licensing guidance](https://dbus.freedesktop.org/doc/dbus-faq.html) and the exact installed copyright hash are retained in source evidence. The final driver dynamically links libdbus-1.so.3; no release/license approval follows from this author check. Linux build environments need **libdbus-1-dev + pkg-config** (or distribution equivalents); deployed Linux needs compatible libdbus-1. No vendored libdbus feature is selected. Downstream CI/package qualification is a delivery task, not completed by this provider change.

Maintenance/provenance checked on 2026-10-18: all four selected repositories are under `open-source-cooperative`, unarchived and enabled; crates.io lists `brotskydotcom` (Daniel Brotsky) as owner. Selected releases were published on 2026-10-13 (core), 2026-08-06 (Apple), 2026-05-24 (Windows), and 2026-08-15 (zbus), all non-yanked at observation. ## API and error boundary

On macOS/Windows, use explicit `Store::new` / `new_with_configuration` and `CredentialStoreApi::build(service, user, modifiers)` to obtain `keyring_core::Entry`; then `set_password`, `get_password` and `delete_credential` inside the private adapter. The [store API](https://github.com/open-source-cooperative/keyring-core/blob/50fe5c44fa3dc46cdf792acfe5116e1e8ebc2e0b/src/api.rs#L174-L235) and [Entry methods](https://github.com/open-source-cooperative/keyring-core/blob/50fe5c44fa3dc46cdf792acfe5116e1e8ebc2e0b/src/lib.rs#L194-L285) do not supply our ledger, authorization, cancellation or durable settlement semantics. Do not route concurrent accounts/migrations through a mutable process-wide default store. A constructor succeeding or `persistence()` returning `UntilDelete` proves neither availability nor a durable write.

| Observed crate result | Adapter contract |
| --- | --- |
| `NoEntry` | Exact lookup absent now; never provider absence, writer settlement or restoration permission. |
| `NoStorageAccess` / `PlatformFailure` | Inspect only qualified provider-specific evidence to classify locked, denied, unavailable, transient or other. Neither top-level variant means “wrong Nextcloud password” or proves the provider is absent. |
| `BadEncoding`, `BadDataFormat`, `BadStoreFormat` | Corrupt/format recovery. The first two can contain raw bytes; neither `Debug` nor an arbitrary error/source string is safe to log. |
| `Ambiguous` | Conflicting matches: recovery required; never select the first item or delete all matches. |
| `Invalid`, `TooLong` | Invalid configuration/input or provider limit; no truncation, auto-overwrite or silent backend switch. |
| `NoDefaultStore`, `NotSupportedByStore`, future non-exhaustive variants | Configuration/unsupported/other as evidenced. No default store is a wiring problem, not proof that the OS has no vault. Preserve an allowlisted code and safe retry state only. |

The non-exhaustive [core error source](https://github.com/open-source-cooperative/keyring-core/blob/50fe5c44fa3dc46cdf792acfe5116e1e8ebc2e0b/src/error.rs#L15-L123) includes raw-byte payloads and diagnostic formatting that must stay private. Native distinctions require more than the portable enum:

- Apple maps several status codes to `NoStorageAccess`, item-not-found to `NoEntry`, and other codes to `PlatformFailure`. `errSecInteractionNotAllowed` alone is not proof of a locked keychain. The selected module does not expose all Keychain attributes; access/signing/synchronization cannot be claimed from its constructor. [Mapping](https://github.com/open-source-cooperative/apple-native-keyring-store/blob/78cdfff31e8a6579119b75ff7cbfeae7d4fc7d0a/src/keychain.rs#L367-L378), [attribute limitation](https://github.com/open-source-cooperative/apple-native-keyring-store/blob/78cdfff31e8a6579119b75ff7cbfeae7d4fc7d0a/src/keychain.rs#L28-L66).
- Windows maps `ERROR_NOT_FOUND` to `NoEntry`, `ERROR_NO_SUCH_LOGON_SESSION` to `NoStorageAccess`, and other native codes to `PlatformFailure`. Its numeric wrapper is in a private module; there is no advertised public typed-code accessor. I2 uses the pinned top-level missing-logon mapping only and retains `Other` for opaque platform failures; it never parses formatted source errors. Qualification must establish any further allowlisted mapping; never expose arbitrary source strings or guess a lock. Native denial/missing-logon tests are required before support claims. [Error wrapper/mapping](https://github.com/open-source-cooperative/windows-native-keyring-store/blob/65bf68219cab395e7b508f57df1aa0899d20face/src/utils.rs#L371-L403).
- Linux retains typed secret-service/zbus preflight categories. The new path maps only fixed D-Bus protocol error names (never error body/address text): IsLocked or disabled Prompt → Locked; AccessDenied/AuthFailed → AccessDenied; ServiceUnknown/NameHasNoOwner → Unavailable; NoReply/Disconnected/Timeout → TemporarilyUnavailable; UnknownObject or exact absent lookup → Missing; unknown → Other. A missing default collection is Unavailable. Search ambiguity is Conflict. Setter completion alone is not settlement. A lock/prompt refusal after write dispatch remains conservatively unknown unless non-write is independently proved. Background restoration/maintenance never requests an unlock or prompt; the user can unlock in the OS and explicitly retry.

Run synchronous native/file calls on bounded identity workers, never GPUI. Preserve account serialization and the Windows provider's [thread-ordering warning](https://github.com/open-source-cooperative/windows-native-keyring-store/blob/65bf68219cab395e7b508f57df1aa0899d20face/src/lib.rs#L75-L88). A timeout or observer drop does not cancel an OS write. No selected crate advertises a durable operation-ID query or post-crash writer-settlement oracle. The adapter still owes ADR-003's recovery barrier, suppression, distinct N/P identities and exact cleanup. The crates' time-based process-instance IDs must not be persisted as stable store bindings ([Apple](https://github.com/open-source-cooperative/apple-native-keyring-store/blob/78cdfff31e8a6579119b75ff7cbfeae7d4fc7d0a/src/keychain.rs#L199-L215), [zbus](https://github.com/open-source-cooperative/zbus-secret-service-keyring-store/blob/a97612aa64dd0148ad2504b3a9d4d82ca94e070b/src/store.rs#L48-L63)).

## Observed Talk Desktop behavior

Research checked official `nextcloud/talk-desktop` **main `4fb66173e85dcbcdbdf58c4952cbb84dc2b0728b`** and latest published **[v2.3.3](https://github.com/nextcloud/talk-desktop/releases/tag/v2.3.3)** at **`d6ee178a984d108a52bc6c279b5d8d982daa74d5`**, observed on 2026-10-18. The five relevant source files listed in the manifest are byte-identical between those commits. The inspected flow:

1. The credentials type identifies its password as an app password; login assigns the result to `appData.credentials`, then persists after metadata retrieval. [Credential type](https://github.com/nextcloud/talk-desktop/blob/d6ee178a984d108a52bc6c279b5d8d982daa74d5/src/authentication/loginFlowV1.service.ts#L6-L13), [save path](https://github.com/nextcloud/talk-desktop/blob/d6ee178a984d108a52bc6c279b5d8d982daa74d5/src/authentication/renderer/AuthenticationApp.vue#L158-L180).
2. `AppData` includes credentials in JSON and writes/reads that JSON through `localStorage`; its source still has a safeStorage TODO. There is no OS-store availability branch or application encryption in this inspected persistence path. [Serialization and restoration](https://github.com/nextcloud/talk-desktop/blob/d6ee178a984d108a52bc6c279b5d8d982daa74d5/src/app/AppData.js#L6-L95).
3. Startup restores the data and uses its credentials to establish authenticated requests; the main process selects an app-specific user-data path. [Startup](https://github.com/nextcloud/talk-desktop/blob/d6ee178a984d108a52bc6c279b5d8d982daa74d5/src/welcome/welcome.main.ts#L28-L45), [user-data path](https://github.com/nextcloud/talk-desktop/blob/d6ee178a984d108a52bc6c279b5d8d982daa74d5/src/main.js#L40-L43).

**Inference limited to those sources:** this path intends persistent app-credential reuse without depending on a secret-store fallback, rather than requiring a new login each launch. It is not evidence of a tested runtime, owner-only modes/DACLs, atomicity, crash safety or our generation/ledger guarantees. Our native-first, explicit unencrypted-file fallback is the user's chosen behavior; it does not copy the upstream localStorage/Electron implementation or claim undocumented security equivalence. Upstream files carry AGPL-3.0-or-later notices and are cited as research only, not incorporated as code.

## I2 implementation additions

The additional exact, default-feature-disabled dependencies are `rusqlite 0.40.2` (`bundled`, `limits`), `dirs 5.0.1`, Unix `rustix 1.1.5` (`std`, `fs`, `process`), Linux `secret-service 5.2.0` (`crypto-rust`) and `zbus 5.19.0` (`blocking-api`, `async-io`), macOS `exacl 0.13.0` and `security-framework 3.7.0`, and Windows `windows-permissions 0.2.4`, `winapi-util 0.1.11`, `atomicwrites 0.4.4`. The source manifest records archives, checksums, licenses and purpose. Existing GPUI/unicode/libc pins stay unchanged. There is no application unsafe-code exception. The direct Security Framework edge reads typed OSStatus only; its upstream maintenance metadata is not a native qualification.

Linux preflights the actual user Secret Service and unlocked default collection, then independently uses the non-unlocking prompt-disabled provider methods. A preflight alone is not atomic with a lock race. Absent D-Bus/service/default collection, denied access and locked state remain safe typed failures. No automatic unlock/prompt or migration occurs. Explicit native retry follows OS-side unlock; durable plaintext file, optional session-only and cancellation remain available to composition. Real GNOME process/service restart is exercised; KWallet remains unqualified.

The immutable file provider uses no-replace installation, file and parent flush, owner/mode/ACL checks, and exact generation names. Windows uses safe handle/ACL wrappers and same-directory MoveFileEx with WRITE_THROUGH; GNU cross-compilation is not a Windows runtime/DACL test. macOS uses user Keychain and fullfsync/ACL paths; actual Apple hardware evidence remains pending. Native setter completion alone never commits restoration eligibility: read-back/settlement, current validation, attempt, revision and suppression remain separate.

## Remaining qualification and review

The I2 implementation adds backend-qualified identities, provider routing, explicit storage choices and bounded runtime operations in the existing adapter. The source manifest does not itself prove file/path/ACL/atomicity or native settlement; see the exact author tests and platform limits. Do not infer OS support, native app functionality or a performance result from upstream CI/docs targets.

Required evidence is [CT-003](../../compatibility/test-matrix.md#ct-003), [V.AUTH.STORE-01–16](../../quality/verification.md#vauthstore--uncertain-storage-transitions) and V.AUTH.LOSS across the selected provider combinations, with both real Nextcloud/Talk families where authentication is claimed. Product support claims require actual candidate/platform evidence under Q.VER; provider selection alone supplies no runtime qualification.
