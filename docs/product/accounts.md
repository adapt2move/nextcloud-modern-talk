# Accounts and authentication

This document defines account and authentication behavior; [security.md](../quality/security.md) owns secret handling, trust boundaries, and storage interfaces. Login uses system-browser Login Flow v2 as documented for [NC34](https://docs.nextcloud.com/server/34/developer_manual/client_apis/LoginFlow/index.html#login-flow-v2) and [NC35](https://docs.nextcloud.com/server/35/developer_manual/client_apis/LoginFlow/index.html#login-flow-v2); no embedded browser is required.

## Spec amendment — AMEND-AUTH-STORAGE-01

On 2026-10-18 the user required a ready-made Rust abstraction for OS stores and a **durable fallback comparable in purpose to Talk Desktop**, explicitly stating **“Keine verschlüsselung”**. The file fallback below is therefore **unencrypted**, with no master password, KDF, application encryption or extra approval workflow. OS-native stores remain preferred and retain their normal OS protection. Normal sign-in must persist the account. It offers native storage or an explicitly chosen durable private file; it does not offer temporary/session-only sign-in or silently fall back to it. Only app credentials are eligible, never the user's primary password. [ADR-006](../architecture/decisions/006-credential-providers.md) records the exact crate selection and the narrower observed Talk Desktop behavior.

The [feature inventory](../compatibility/feature-inventory.md) records implementation and verification scope; [current state](../status.md) records actual limitations. These requirements do not themselves establish a provider or platform pass.

## AUTH-001

**Validate and connect to a server (P1).** Accept a server URL, normalize a missing scheme to HTTPS, and preserve installation subpaths. Show the destination before browser login. Distinguish invalid address, unavailable network, TLS failure, maintenance, missing Talk, and an unverified version family. Do not send credentials over unencrypted HTTP or silently bypass certificate failures. Local disposable-server exceptions, if later provided, belong to an explicit development configuration governed by the security contract.

Acceptance: `https://cloud.example.test/nextcloud/` remains under that installation path throughout login and API use. A certificate error leaves the account unconnected with a retry/edit action. Server discovery does not request microphone/camera permission.

## AUTH-002

**Authorize through the system browser (P1).** Start Login Flow v2, open the validated login URL, and poll with a cancellable, bounded lifetime. The browser handles password, 2FA, SSO, and consent; the client receives a device-specific app password. Treat an expected “not authorized yet” poll result as pending, not a failed account. Show “Im Browser anmelden”, “Warten auf Freigabe”, cancel, and restart after expiry. Keep login name distinct from server user ID.

Acceptance: success establishes exactly one account after identity/capability validation; duplicate poll results or late success after cancellation cannot overwrite another account. Expiry, browser-launch failure, denied consent, and a lost one-time poll response provide a clean restart without credentials in URLs, logs, crash text, or clipboard. Never request the user's primary password as an automatic fallback. A future manual app-password entry is explicit, uses the same secure-storage rules, and must not be mislabeled as SSO support.

## AUTH-003

**Persist app credentials with an explicit storage backend (P1 contract; additional OS clients P4).** Prefer macOS Keychain, Windows Credential Manager or an available, qualified Linux Secret Service implementation through the pinned **keyring-core and native provider crates** in [ADR-006](../architecture/decisions/006-credential-providers.md#selected-crates-and-platforms). The platform/storage contract is defined now; it does not claim a Windows/Linux UI or native adapter exists. If native storage is absent/unavailable, offer durable unencrypted private-file storage under AUTH-004. A completed normal sign-in requires confirmed durable storage and committed restoration eligibility; failure offers retry or cancellation. Account settings and the restoration ledger hold only nonsecret references, backend choice and restoration/cleanup metadata; secret bytes belong only to the chosen provider or the live session.

Follow [Q.SEC-03](../quality/security.md#qsec-03--os-vault-contract): commit the write intent and selected backend before dispatch, stage new generation `N` separately from retained `P`, and suppress account restoration while the attempt is unresolved. Show the actual backend and durable-login success only after confirmed storage and committed eligibility for that exact account/**backend**/generation. For the file backend use “Auf diesem Gerät gespeichert (unverschlüsselte Datei)”; filesystem permissions must not be labelled encryption or equivalent to Keychain. Provider acknowledgement alone is insufficient if activation metadata did not commit.

Acceptance: restart requires committed eligibility and an accessible confirmed entry for the **same qualified provider identity** and generation. Restore a valid selected file credential without a new browser login solely because native storage is unavailable. An unresolved, abandoned or rejected credential cannot restore by provider enumeration. Missing/corrupt metadata or a changed provider binding requires explicit recovery. Native-store recovery never changes a saved file/session choice. Failure to commit pre-write intent dispatches no write. Duplicate account addition never merges by display name, backend availability or generation number. Store errors expose no secret bytes. Exercise [V.AUTH.STORE](../quality/verification.md#vauthstore--uncertain-storage-transitions).

## AUTH-004

**Offer durable private-file persistence (P1).** When native storage is absent/unavailable, the ordinary continuation **“Auf diesem Gerät speichern”** offers an unencrypted credential file, alongside retry and cancel. There is no session-only option in normal sign-in. Explain the file mode in that choice and remember its committed selection; no master-password/encryption setup or separate approval dialog is required. Do not force a fresh login on every launch merely because the OS has no usable secret service. Locked/denied/corrupt stores retain their distinct recovery paths under AUTH-005 and may also offer this explicit file choice for a valid available credential.

“Protected” for the file means a private per-user application-data directory, POSIX directories `0700` and files `0600`, or a verified owner-restricted Windows DACL. This is access control, **not encryption or protection from the same user, an administrator, a compromised process or copied backups**. Never place the file in public/shared/synced/temporary directories or use settings, logs, environment variables, clipboard, diagnostics or a shared cache as a substitute. [Q.SEC-04](../quality/security.md#private-file-provider) defines owner/path/permission checks and atomic durability. Failed checks block that file operation; offer repair/retry or cancel while preserving any still-valid existing memory session. A failed save cannot silently activate a temporary replacement.

For file storage, a fresh committed save intent selects a new backend-qualified `N`; confirmed durable file installation and committed eligibility precede success. An abandoned native write must first be reconciled without deleting retained `P`; selecting file storage cannot bypass an uncertain writer, account suppression or cancellation. A failure never silently selects another backend. The UI preserves the pending choice and explains any unresolved save; it does not promise durable login prematurely.

For an **existing temporary session or legacy session-only transition**, preserve the established recovery guarantees: commit suppression of automatic restoration of **all** account generations/backends before replacement activation. If suppression cannot commit, explain the restart-safety failure and offer repair/retry or cancellation retaining the prior valid session. No replacement activates under an unfulfilled session-only promise. [Q.SEC-03/04](../quality/security.md#restoration-and-uncertain-writes) governs both modes.

With a known non-write or confirmed cleanup, explain that the credential is held only for this application session and login is needed after exit. With an earlier uncertain provider write, instead show “Nur für diese Sitzung aktiv. Ein Speicherversuch ist ungeklärt; automatische Anmeldung ist gesperrt.” Abandon and reconcile only the attempted generation; keep residual-storage status visible through cancellation/restart until both writer settlement and deletion/absence are confirmed. An early missing-item result cannot prove cleanup while a writer may still complete. Closing a window need not end the session; logout or process exit does. Do not promise erasure from OS-managed memory, swap or backups.

Acceptance: [V.AUTH.STORE-01–16](../quality/verification.md#vauthstore--uncertain-storage-transitions) covers absent D-Bus/Secret Service, both persistent providers, file permissions/ACLs, concurrent/failed writes, crashes, restart, explicit migration, legacy session-only handling and all uncertain-write boundaries. File mode restores only its exact eligible credential; session-only restores neither old nor new credentials, even if residual items remain. Session-only makes no further provider write without explicit save and creates no secret-bearing file or new durable content cache. No late completion activates an abandoned `N`. Cancel with no prior session leaves the account unconnected; deliberate cancel-and-retain follows AUTH-005. Ordinary private-file persistence is authorized by this amendment; secret-bearing error/recovery exports remain prohibited.

## AUTH-005

**Distinguish unavailable, locked, denied, corrupt and missing-entry states (P1).** An absent Linux session bus/Secret Service is different from a locked collection, access refusal or damaged item. A locked Keychain is not an absent account. Show one recoverable OS unlock/retry path; respect dismissal/denial and do not repeat prompts in the background. Missing entries need reauthentication unless the same account still has a valid memory credential. A transient failure may leave that session working, without claiming a new save succeeded. Corruption or unsafe file permissions require explicit repair/recovery and cannot trigger overwrite or backend switching.

**Later save or migration is explicit.** Keep the selected file/native/session mode across restart and OS-store recovery. “Im Betriebssystem speichern” or a deliberate change to file mode starts a new backend-qualified generation after prior reconciliation. Use a still-valid memory credential or explicitly read/revalidate the selected source credential; if inaccessible, use fresh browser authorization, never the primary password. Commit the target choice/intent, confirm the target write, then atomically commit sole target eligibility. Retiring the source needs the stated replacement/removal authority and its own exact cleanup record. Failed migration leaves the last committed disposition in force, keeps the source untouched and reports uncertainty; deliberate cancel-and-retain may restore only validated, named `P`. No union of source and target generations is restorable.

Acceptance: fallback/cleanup never deletes, overwrites or recreates retained `P`, even across providers. Session-only leaves `P` ineligible. Deliberate cancel-and-retain commits eligibility for that exact provider/`P` alone; failed retention reports remaining suppression rather than promising restoration. An inaccessible old secret cannot be copied into a file or recovered into memory without valid authorization. Unlock, provider recovery, a stale save receipt or a late abandoned write never enables persistence. “Forget account” remains a separate explicit action.

## AUTH-006

**Isolate multiple accounts and guest sessions (P1; guest entry P2).** Account switch preserves a distinct selected room and draft state. Requests, caches, media callbacks, notifications, and server settings carry account identity. Deep links identify their destination; never silently send a message using the currently selected unrelated account. Guest sessions are explicitly named and isolated from authenticated sessions.

Acceptance: two servers with identical room tokens, usernames, and display names cannot exchange drafts, credentials, notifications, or files. A background response from a removed account is discarded. Switching accounts during a call keeps the active call's account visible and does not start a second microphone session.

## AUTH-007

**Recover from expired or revoked authorization (P1).** On **confirmed account authorization loss**, present “Erneut anmelden” and execute [Q.SEC-05](../quality/security.md#confirmed-account-authorization-loss): invalidate the account's runtime generation, close admission of authenticated work, cancel its requests/transfers/sends/signaling/reconnect work, disable local media publication and stop owned microphone/camera/screen capture. Local shutdown and rejection of obsolete callbacks cannot wait for server leave, revocation, vault access or metadata success. The bootstrap must define the account-rejection classifier and numeric capture/device-release deadline. An action denial, expired room/guest/signaling session, network failure, maintenance or rate limit is not itself confirmed account rejection; recover only the affected scope.

Suppress automatic reuse of every stored generation for the rejected account. If durable suppression fails, finish local shutdown and disclose that suppression across restart is unconfirmed. Preserve account identity, permitted unsent drafts and unrelated accounts. A request already accepted by the server cannot be recalled; an uncertain send remains unsent/delivery-unknown until reconciled. Resume only after validated new authorization for the intended user, a new runtime generation, fresh capabilities/room/consent/security/session checks and a deliberate send retry or call rejoin. Reauthentication alone never restarts capture or replays sends.

Acceptance: [V.AUTH.LOSS-01–03](../quality/verification.md#vauthloss--confirmed-account-authorization-loss) rejects late login/request/policy/media/reconnect successes from the invalidated generation while a second account remains active. Revoke during a call and pending send, drop the leave response, fail suppression metadata and verify actual local shutdown and truthful storage status. Reauthorization to another user inherits no pending work. Rejoin preserves mute/camera intent and CALL-001/004's direct-accept versus voluntary-prejoin distinction.

## AUTH-008

**Sign out and remove accounts deliberately (P1).** Explain active calls, pending sends, downloads, and local drafts before removing an account. Stop its activity and remove accessible local secrets and cached data under the security policy. Attempt device-token revocation when supported and reachable; report an unsuccessful remote revocation separately with guidance to revoke the device in NextCloud. Do not claim that local removal revoked remote access.

Acceptance: offline removal completes locally; no background retry uses removed credentials. If a locked/denied native store or failed private-file deletion prevents cleanup, preserve a nonsecret pending-cleanup marker bound to that backend, suppress restoration across every backend, and report incomplete cleanup; complete it when access is restored. If durable suppression itself fails, still stop local access and report restart suppression as unconfirmed under Q.SEC-05. Deleting an older retained credential requires authorized replacement or explicit logout/removal. Separately, abandoning an authorization/storage attempt permits exact-generation cleanup, including a late write, under AUTH-003–005; this never authorizes deletion of an unrelated or retained older item. No deletion claim precedes confirmed settlement and absence.

## AUTH-009

**Treat storage of content separately from storage of credentials (P1).** Session-only credential mode does not silently enable persistent message, draft, file, or diagnostic storage. Use the security contract's account-scoped cache policy; default to memory when a required protected cache key cannot be accessed. Explain when a draft cannot survive restart. Downloads intentionally saved by the user are separate from the app cache.

The unencrypted **credential-file** decision does not change that content/cache policy, place content keys in the file, or authorize plaintext shared caches. Only the app credential and bounded binding/format fields belong to the file provider.

Acceptance: locked/missing storage cannot cause a plaintext cache fallback. A storage failure preserves current in-memory text where feasible and explicitly reports the lack of persistence. Clearing a cache does not delete files the user explicitly saved outside it.
