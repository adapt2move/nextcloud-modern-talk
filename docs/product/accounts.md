# Accounts and authentication

Status: **Planned**. This document owns visible behavior; [security.md](../quality/security.md) owns secret handling, trust boundaries, and storage interfaces. Login uses system-browser Login Flow v2 as documented for [NC34](https://docs.nextcloud.com/server/34/developer_manual/client_apis/LoginFlow/index.html#login-flow-v2) and [NC35](https://docs.nextcloud.com/server/35/developer_manual/client_apis/LoginFlow/index.html#login-flow-v2); no embedded browser is required.

## AUTH-001

**Validate and connect to a server (P1).** Accept a server URL, normalize a missing scheme to HTTPS, and preserve installation subpaths. Show the destination before browser login. Distinguish invalid address, unavailable network, TLS failure, maintenance, missing Talk, and an unverified version family. Do not send credentials over unencrypted HTTP or silently bypass certificate failures. Local disposable-server exceptions, if later provided, belong to an explicit development configuration governed by the security contract.

Acceptance: `https://cloud.example.test/nextcloud/` remains under that installation path throughout login and API use. A certificate error leaves the account unconnected with a retry/edit action. Server discovery does not request microphone/camera permission.

## AUTH-002

**Authorize through the system browser (P1).** Start Login Flow v2, open the validated login URL, and poll with a cancellable, bounded lifetime. The browser handles password, 2FA, SSO, and consent; the client receives a device-specific app password. Treat an expected “not authorized yet” poll result as pending, not a failed account. Show “Im Browser anmelden”, “Warten auf Freigabe”, cancel, and restart after expiry. Keep login name distinct from server user ID.

Acceptance: success establishes exactly one account after identity/capability validation; duplicate poll results or late success after cancellation cannot overwrite another account. Expiry, browser-launch failure, denied consent, and a lost one-time poll response provide a clean restart without credentials in URLs, logs, crash text, or clipboard. Never request the user's primary password as an automatic fallback. A future manual app-password entry is explicit, uses the same secure-storage rules, and must not be mislabeled as SSO support.

## AUTH-003

**Persist credentials only in an OS secret store (P1).** macOS uses Keychain. Future Windows/Linux adapters must provide qualified access-controlled secret storage and report their actual availability. Account settings store only nonsecret references and restoration/cleanup metadata. Follow [Q.SEC-03](../quality/security.md#qsec-03--os-vault-contract): commit the write intent before dispatch, stage a new generation separately from any retained older item, and suppress account restoration while the attempt is unresolved. Show “Sicher gespeichert” only after the write is confirmed and restoration eligibility for that exact account/generation is committed. A provider acknowledgement alone is insufficient if activation metadata could not be committed.

Acceptance: restart requires both committed restoration eligibility and a confirmed accessible entry for the same generation. An accessible item left by an unresolved write, fallback or rejected account cannot restore automatically. Missing/corrupt/incomplete metadata offers explicit recovery instead of guessing from vault enumeration. Failure to commit pre-write intent dispatches no write. Duplicate account addition offers to use/re-authorize the existing account and never merges by display name alone. Store errors expose no secret bytes. Exercise the crash boundaries in [V.AUTH.STORE](../quality/verification.md#vauthstore--uncertain-storage-transitions).

## AUTH-004

**Use a safe session-only fallback (P1).** When persistent secret storage is missing, unavailable, denied, or cannot save a newly authorized credential, offer **“Nur für diese Sitzung fortfahren”** as the default continuation, retry and cancel. Fallback requires the user's choice. Before activating a replacement session-only credential, durably suppress automatic restoration of **all** account generations, including an older retained item. If suppression cannot be committed, explain the restart-safety failure and offer repair/retry or cancellation retaining the prior valid session; do not activate the replacement under a session-only promise. [Q.SEC-03/04](../quality/security.md#restoration-and-uncertain-writes) governs the transition.

With a known non-write or confirmed cleanup, explain that the credential is held only for this application session and login is needed after exit. With an earlier uncertain provider write, instead show “Nur für diese Sitzung aktiv. Ein Speicherversuch ist ungeklärt; automatische Anmeldung ist gesperrt.” Abandon and reconcile only the attempted generation; keep residual-storage status visible through cancellation/restart until both writer settlement and deletion/absence are confirmed. An early missing-item result cannot prove cleanup while a writer may still complete. Closing a window need not end the session; logout or process exit does. Do not promise erasure from OS-managed memory, swap or backups.

Acceptance: [V.AUTH.STORE-01–06](../quality/verification.md#vauthstore--uncertain-storage-transitions) covers every store error, committed-but-unacknowledged writes, fallback/cancel followed by late success, crash/restart and failed metadata updates. No late completion activates an abandoned generation. Chosen session-only mode restores neither old nor new credentials after restart, even if residual items remain. It makes no further vault write without an explicit save action and creates no secret-bearing recovery file, ordinary-file/preference/log/environment fallback or new durable content cache. Cancel with no prior session leaves the account unconnected; deliberate cancel-and-retain follows AUTH-005. Recovery of the vault does not silently re-enable persistence. An encrypted-file fallback remains a **future proposal**, separately reviewed and opt-in, excluded from P1 and never using an embedded/default key.

## AUTH-005

**Distinguish locked, denied, missing, and missing-entry states (P1).** A locked Keychain is not an absent account or a lost credential. Show a single recoverable “Schlüsselbund entsperren”/retry path without repeated OS prompts. If access is denied, respect the decision and offer retry or browser reauthentication for a session-only credential. If the store exists but an entry is absent, explain that reauthentication is needed. A transient lock may leave an already authenticated in-memory session working; do not claim new persistence succeeded.

Acceptance: fallback leaves an intentionally retained older item untouched and ineligible for automatic restoration. Cleanup of a newly attempted, abandoned generation is permitted and must not delete, overwrite or recreate that older item. If the user cancels replacement and deliberately retains a still-valid older session, commit eligibility for that named generation alone; the abandoned replacement never activates. If that retention decision cannot be committed, report the remaining suppression/uncertainty under Q.SEC-03 rather than promising restoration. An inaccessible old secret requires fresh browser authorization or an already valid in-memory session for session-only use. After unlock, re-check identity and ask explicitly before saving/replacing; the user may remain session-only. No repeated background prompts occur. “Forget account” remains a separate explicit action.

## AUTH-006

**Isolate multiple accounts and guest sessions (P1; guest entry P2).** Account switch preserves a distinct selected room and draft state. Requests, caches, media callbacks, notifications, and server settings carry account identity. Deep links identify their destination; never silently send a message using the currently selected unrelated account. Guest sessions are explicitly named and isolated from authenticated sessions.

Acceptance: two servers with identical room tokens, usernames, and display names cannot exchange drafts, credentials, notifications, or files. A background response from a removed account is discarded. Switching accounts during a call keeps the active call's account visible and does not start a second microphone session.

## AUTH-007

**Recover from expired or revoked authorization (P1).** On **confirmed account authorization loss**, present “Erneut anmelden” and execute [Q.SEC-05](../quality/security.md#confirmed-account-authorization-loss): invalidate the account's runtime generation, close admission of authenticated work, cancel its requests/transfers/sends/signaling/reconnect work, disable local media publication and stop owned microphone/camera/screen capture. Local shutdown and rejection of obsolete callbacks cannot wait for server leave, revocation, vault access or metadata success. The bootstrap must define the account-rejection classifier and numeric capture/device-release deadline. An action denial, expired room/guest/signaling session, network failure, maintenance or rate limit is not itself confirmed account rejection; recover only the affected scope.

Suppress automatic reuse of every stored generation for the rejected account. If durable suppression fails, finish local shutdown and disclose that suppression across restart is unconfirmed. Preserve account identity, permitted unsent drafts and unrelated accounts. A request already accepted by the server cannot be recalled; an uncertain send remains unsent/delivery-unknown until reconciled. Resume only after validated new authorization for the intended user, a new runtime generation, fresh capabilities/room/consent/security/session checks and a deliberate send retry or call rejoin. Reauthentication alone never restarts capture or replays sends.

Acceptance: [V.AUTH.LOSS-01–03](../quality/verification.md#vauthloss--confirmed-account-authorization-loss) rejects late login/request/policy/media/reconnect successes from the invalidated generation while a second account remains active. Revoke during a call and pending send, drop the leave response, fail suppression metadata and verify actual local shutdown and truthful storage status. Reauthorization to another user inherits no pending work. Rejoin preserves mute/camera intent and CALL-001/004's direct-accept versus voluntary-prejoin distinction.

## AUTH-008

**Sign out and remove accounts deliberately (P1).** Explain active calls, pending sends, downloads, and local drafts before removing an account. Stop its activity and remove accessible local secrets and cached data under the security policy. Attempt device-token revocation when supported and reachable; report an unsuccessful remote revocation separately with guidance to revoke the device in Nextcloud. Do not claim that local removal revoked remote access.

Acceptance: offline removal completes locally; no background retry uses removed credentials. If a locked/denied secret store prevents deletion, preserve a nonsecret pending-cleanup marker, suppress automatic restoration, and report incomplete cleanup; complete it when access is restored. If durable suppression itself fails, still stop local access and report restart suppression as unconfirmed under Q.SEC-05. Deleting an older retained credential requires authorized replacement or explicit logout/removal. Separately, abandoning an authorization/storage attempt permits exact-generation cleanup, including a late write, under AUTH-003–005; this never authorizes deletion of an unrelated or retained older item. No deletion claim precedes confirmed settlement and absence.

## AUTH-009

**Treat storage of content separately from storage of credentials (P1).** Session-only credential mode does not silently enable persistent message, draft, file, or diagnostic storage. Use the security contract's account-scoped cache policy; default to memory when a required protected cache key cannot be accessed. Explain when a draft cannot survive restart. Downloads intentionally saved by the user are separate from the app cache.

Acceptance: locked/missing storage cannot cause a plaintext cache fallback. A storage failure preserves current in-memory text where feasible and explicitly reports the lack of persistence. Clearing a cache does not delete files the user explicitly saved outside it.
