# Messages, threads, and retrieval

These requirements define messaging behavior. Implemented paths and remaining parity work are described in [current state](../status.md) and the [feature inventory](../compatibility/feature-inventory.md). Sources: [chat, reaction, thread, scheduling, and capability contracts](../compatibility/baselines-and-sources.md#protocol-sources). All writes require current membership, relevant permissions, and supported room/host behavior.

## MSG-001

**Read and paginate history (P1).** Render text, rich objects, system events, deleted/edited markers, timestamps, and reply context with stable message identities. Preserve scroll position when older messages arrive. Separate first load, older-history load, empty history, partial history, and failed pagination. Do not execute HTML or scripts from any message or object.

Display message times as `HH:MM` in the system timezone, without a UTC suffix or a timezone selector. The platform owner observes the system zone outside the UI thread; rendering uses that cached observation.

Adjacent ordinary messages from the same confirmed actor form one visual group when their timestamps are at most two minutes apart on the same local calendar day. Unknown actor identity, a different sender, system/deleted messages, replies and thread boundaries start a new group. A display name never establishes actor identity. Continuations retain their timestamp, selection and message actions without repeating the sender/avatar header.

Switching to a previously opened conversation restores its retained history immediately, then reconciles changes in the background. Retention is bounded and scoped to the account, host, runtime and conversation; logout, account removal and loss of access retire the corresponding content. A transient connection failure preserves already loaded history for offline reading. Eligible ordinary rooms restore bounded history across restarts under [AUTH-009](accounts.md#auth-009). Restricted, unknown-policy and session-only content stays in memory. Cached data never restores permission or authentication authority.

After a successful connection and room-list read, prefetch one newest page for up to four recently active, unarchived conversations with known read permission. Exclude classified, sensitive and unknown-policy rooms. Admit one speculative read at a time, with at most 50 messages per room; foreground navigation takes priority. Prefetch never changes selection, joins a room, sends notifications or marks messages read. At capacity, skip speculative rooms rather than evicting opened history. Queued prefetch expires after 60 seconds instead of accumulating behind foreground work. Repeated list refreshes do not restart a completed prefetch plan. Account retirement and observed access loss retire its queued work and completion tickets.

Reconciliation after a send retains the event cursor and does not restart the initial-history loading state. An already loaded empty conversation remains ready during background reads. Older-page requests keep their own progress and failure state when a concurrent background read completes.

Load an older page when the reader reaches the top of the loaded history, with one outstanding request per scoped cursor. Loading or retry controls belong at that boundary, not in a permanent bar above the timeline. Preserve the visible message anchor when prepending a page; avoid repeatedly requesting a failed or unchanged cursor.

Acceptance: duplicate/out-of-order delivery produces one canonical message per ID without jumping the reader to the bottom. Unknown system events/rich objects show an intelligible fallback. A deleted/expired parent is identified as unavailable without exposing its cached text. The room-list preview is not assumed to contain complete reaction or parent data. A deleted message retains its known author/avatar and deletion marker, including at a grouping boundary. It exposes no overflow menu, reply shortcut, reaction controls, retained quote or attachment. Expiry and loss of access still retire the avatar and content.

Call activity pairs its text with a status icon. Incoming and outgoing calls have directional telephone icons; joined, left and ended calls remain neutral. Missed and unanswered calls use red status text and an unsuccessful-call icon, while timestamps stay muted. Classify only untranslated canonical system events, never message text or a localized phrase. Preserve the observed status in ordinary durable history. Older cached rows without event metadata may receive a bounded background metadata read without changing the reading window, pagination/event cursors or read markers.

Newly appended incoming and own messages appear with a short, subtle entry transition: a 200 ms eased fade and small upward movement, slightly more pronounced for one's own send. Motion must not change measured row heights, delivery state or input responsiveness. Animate a scoped message once. Initial history, older pages, same-message edits, pending-to-confirmed reconciliation and virtualized row remounts do not replay entry motion. Larger incoming batches settle without individual movement; one's own accepted send can still receive entry feedback. System events appear without decorative movement. Do not infer message identity from matching text or timestamps.

When the reader was already at the end before an incoming append, follow the new end after a 75 ms post-layout delay. This also applies to system events and larger batches. Coalesce a burst without repeatedly extending that delay. Edits, deletions and height changes keep a reader who is already at the end there. A deliberately submitted own message first scrolls the conversation to the bottom, including when the reader was viewing older messages. Its entry animation starts only after a subsequent layout confirms the new bottom position; requesting a scroll must not start the animation clock. Manual upward scrolling, navigating to message context, switching conversation or hiding the timeline cancels pending follow; incoming messages preserve the visible anchor while reading older content. Reduce Motion renders bubbles immediately and follows after layout without decorative delay. Neither animation nor automatic scrolling marks unseen messages read.

## MSG-002

**Compose and format (P1).** Provide multiline text, emoji, supported Markdown, paste, and explicit send. Respect the server message-length limit before sending and preserve text on rejection. Offer a discoverable send-key preference; the default is Enter to send and Shift+Enter for a newline, with IME composition never interpreted as send. Native rendering must safely handle lists, code, quotes, links, and supported emphasis; unsupported syntax stays readable.

Render ordinary message bodies with native CommonMark formatting, including headings, ordered/unordered lists, task markers, emphasis, strikethrough, inline/fenced code and quotes. Recognize explicit Markdown links, web autolinks and bare `http://`, `https://` and `www.` addresses outside code. Show the canonical destination on hover and keyboard focus. Only validated HTTP/HTTPS destinations without credentials or ambiguous control characters can open. HTML and remote Markdown images remain inert text; no preview request follows from parsing.

The composer edits formatted content directly. Completing supported Markdown delimiters or block prefixes replaces them with formatting; editable syntax is hidden. Support emphasis, strikethrough, code, links, headings, lists, task markers and quotes, with native selection, copying and input-method composition addressing the visible text. Bold, italic and inline code also have discoverable keyboard shortcuts. Newlines continue lists and quotes; an empty item exits its block. Canonical Markdown serialization is separate from native UTF-16 offsets and is used consistently for drafts, sends, edits, schedules and captions. Undo restores content and formatting together. Preedit stays tentative, is never submitted, and does not replace the committed draft. Other input fields and concealed entries remain plain text. Copying timeline or composer text copies the displayed characters, preserving code whitespace.

One editor document holds at most 4096 bytes of visible text and canonical Markdown, 256 blocks, 32 links and 64 code groups. Apply edits transactionally within the current server limit; if an edit cannot be represented within these bounds, preserve the previous draft and explain the rejection. A rejected load cannot change the edit, reply or thread target. A changed room must never retain another room's text; preserve an unavailable stored draft without submitting or overwriting it. Receipt cleanup requires the unchanged editor generation and no active composition, including when later edits return to identical text. A smaller server limit retains existing content for correction while preventing submission. Keep at most 16 undo and 16 redo documents plus one preedit baseline. Unsupported syntax remains readable; direct editing does not imply support for arbitrary Notion blocks, tables or embedded content.

One desktop selection owner prepares at most 96 documents and 256 KiB of source. Parsing accepts at most 4 KiB of source and produces at most 8 KiB of text, 256 line records, 512 style spans and 32 links, with 2048 events and 32 nested elements. Excessive or malformed Markdown falls back to readable literal text without active links. Derived text retires when its source is edited, removed, hidden or loses its permitted presentation. Link activation is a deliberate release or keyboard action; dragging selects text. Composition revalidates the account, room, exact source and link ordinal before the OS handoff. At most one handoff waits for at most two seconds; navigation, source changes, expiry or permission loss discard it.

Pasting into an editable draft imports text locally and remains available offline, including when room clipboard-export authority is unknown. Apply the same document limits and composition guard as other input. Copy and Cut export draft content and still require the current room privacy decision; pasting never grants that authority or submits a message.

The composer offers the installed system emoji picker on deliberate activation. Keep the current input target and IME state intact. On systems whose picker copies instead of inserting, explain the paste step; importing that emoji requires no room clipboard-export authority. Missing system support is explicit; opening a picker does not imply that an emoji was selected or inserted.

Keep the composer free of routine status and keyboard-instruction text. Show a small account-specific offline notice after a short sustained failure, or promptly after the system reports a lost network connection. A brief failed request must not flash an offline card. Preserve actionable send errors and explicit reply/edit context. Keep one multiline message field with emoji, send and an additional-content `+` action. The `+` action opens an anchored context menu for attachments, the supported poll flow, scheduling, silent sending and reminders. Keyboard navigation, Escape, focus return and dismissal outside the menu follow the shared popup behavior; stale callbacks cannot act in another conversation. Show explicit reply/edit or silent-send context in a slim dismissible strip. Closing the date/time form preserves the message and reply target. Mentions are entered through `@` in the text itself, without a duplicate standalone mention button. Moving focus into a composer action must not destroy the draft, selection or active editing context.

Reuse recently observed composer capabilities and message limits from history/prefetch instead of requesting them again on selection. The source expires 12 seconds after admission; an old response cannot replace a newer source. Mutations still validate current room policy in the protocol owner. Local staging uses the disabled send action as its pending cue, without an additional loading card in the editor. Keep the draft until the queue confirms staging for its matching request; a durable intent requires a committed transaction. Project the optimistic message immediately and merge the validated canonical response without waiting for another history request.

Acceptance: formatting preview and sent text preserve meaning, Unicode, and line breaks. Links display their destination and open only on deliberate activation under the security policy. Copying code preserves its contents. A permission change disables send while retaining the draft; a read-only timeline does not show a writable composer.

## MSG-003

**Make delivery states truthful (P1).** A pending message progresses through preparing/sending, accepted by server, failed, or delivery-unknown. Server acceptance is not proof of a recipient read. Use a client reference to reconcile optimistic messages with received messages, without assuming the server deduplicates requests. Retain ambiguous sends for read-only reconciliation without assuming safe replay.

Deliberate send, edit, delete, reaction, pin/unpin, forward, reminder, schedule and cancel scheduled message actions enter one account-owned optimistic queue. Each account holds at most 64 intents and 512 KiB of encoded intent data. Reject overflow explicitly and preserve the user's current text. Keep accepted work and correlated results until acknowledged; ordinary cache eviction and cache age never discard a queued intent.

For an eligible durable account and confirmed ordinary room, stage the exact intent in private, unencrypted account storage under AUTH-009. Commit staging before clearing the matching unchanged composer or finishing its edit mode. Restricted, unknown-policy and session-only contexts use the bounded memory queue and must not promise restart recovery. A queued result means local acceptance, not server acceptance or delivery. Apply the optimistic change without a network spinner or a global mutation lock. New desired reaction state may follow an earlier click while its request is running.

An explicitly submitted offline action may dispatch after reconnect. Before each dispatch, validate the current account identity, live runtime, destination, membership, capabilities, room policy and target. An unknown cached permission can admit an intent for later validation; known denial or unsupported behavior remains unavailable. Persist a dispatch marker before an eligible durable write can reach the network. A replaced scope or failed local commit cannot release the write.

Connection errors do not disable local queue admission. After staging, an own outgoing row has a clock indicator with “Waiting for connection” while offline, or “Queued to send” while waiting online. Keep these labels in its tooltip, without a permanent label beside delivery checks. Distinguish queued work from an active send, server acceptance and uncertainty; neither reconnect nor an old read marker can turn a queued message into an accepted or read receipt.

A definitive failure removes that intent's optimistic effect, retains unrelated newer intents and shows a correlated toast. An ambiguous network outcome remains retained within the same queue bounds and shows an uncertainty toast. Reconcile through bounded read-only operations; send/forward correlation examines at most the latest 200 messages. Failure to find a match in that window is not proof that the server did nothing. Never replay an ambiguous POST. A scheduled-message creation without operation correlation remains uncertain until its effect can be established; matching text or time alone cannot justify retrying or removing it.

Failed sends, edits and scheduled creations retain their exact text and target after the editor has cleared. Show one recoverable failure card per selected room, with a clipped selectable preview, a count and previous/next controls when several failures remain. Offer Retry, Edit as draft and Discard. Restoring a copy must not overwrite the current editor or another retained reply/thread draft, and must not acknowledge the original failed record. Restore edits into their edit mode and schedules into the local date/time chooser. Retry replaces the stored record only after the new intent commits atomically; a failed replacement leaves the original recoverable. Only explicit discard removes a failed record without retrying it. Durable failed records survive restart under AUTH-009 and share the queue's existing capacity.

Own confirmed messages show one check for server acceptance. A second check requires a server common-read marker covering that message and confirmed read-receipt support. It describes participants with public read privacy, not undisclosed private readers or an individual reader list. Delivery indicators appear only on own messages, at the bottom-right of the entire message row, including its reactions and attachments. Groups, continuations, edited labels and wrapped text keep that same right edge. Delivery text appears only in the shared tooltip when the pointer rests on the indicator; hovering elsewhere in the row shows no status label. Hover actions are overlays and do not change row geometry. Own messages omit the reply shortcut and align the three-dot menu at the bottom, immediately to the left of the delivery indicator, keeping both controls separate even on compact continuations. Incoming messages retain their reply shortcut and right-aligned menu. Sender and timestamp share one aligned metadata line; long sender names yield space to the timestamp. Pending, failed and uncertain sends use distinct indicators; neither animation nor a local click establishes delivery or read status.

Acceptance: disconnect after possible dispatch shows an uncertain delivery state and starts bounded read-only reconciliation. An unresolved intent remains visible and retained without an automatic write retry. Confirmed pre-submission failure allows a safe retry. Repeated clicks do not send parallel copies. Reauthentication, room removal, or expired permissions never release queued work to the wrong destination.

## MSG-004

**Draft locally and handle offline composition (P1).** Keep a draft per account, conversation, and thread/reply context. Restore text, attachments still available, and recipient context when switching views. Persist only under the approved content-storage policy. Explain session-only retention in the relevant storage settings and before an action that discards unsent work, rather than repeating it in the composer. Typing offline creates a draft, not an outgoing action. Only deliberate submission creates an intent under MSG-003, which may resume after reconnect and fresh validation. Restoring a draft never submits it. Storage settings distinguish unsent draft retention from already staged outgoing work.

Acceptance: any persisted draft restores only for the same account under AUTH-009; session-only mode does not claim recovery. A deleted thread/root or revoked room yields a recoverable draft with explicit destination selection, never a silent post to the main timeline. Logout and cache-clear explain draft loss.

## MSG-005

**Reply and privately reply (P1 reply; P3 private reply).** Quote only supported replyable messages, preserve original references, and let the reader navigate to context. Private reply creates/opens the permitted direct conversation and clearly changes the audience before send; it must not leak a classified/restricted message or imply that the whole source room receives it.

Selecting Reply immediately shows the original author and a preview of up to two text lines above the composer. Composer previews and quotes in message rows share an inset vertical marker with rounded ends, rather than a left border. The preview follows the current message projection; deleted or inaccessible sources show an unavailable state without retaining their text.

Once the matching unchanged reply is queued or server-accepted, clear its quote and return to the unquoted draft in the same destination, preserving any thread and current delivery option. Rejected, failed or uncertain submissions retain the quote for recovery. A late receipt must not clear a newer reply target, edited text or active input-method composition. If the restored destination draft cannot be loaded under the current editor limits, retain its stored text and block submission until it can be recovered.

Acceptance: `isReplyable=false`, deleted parents, unavailable context, and permission removal disable the relevant action with a reason. Private reply requires `private-reply` and source policy; its composer names the private recipient and source context before submission.

Reveal a message's reply arrow and overflow menu when that message is hovered or keyboard-focused, with the reply arrow immediately before the menu and no layout shift. Reply uses the actual server-supported quote/reference operation. These controls retain visible focus and explanations when the message's policy makes an action unavailable.

## MSG-006

**Use real threads (P3; safe reading/fallback P1).** When supported, create named threads, rename when authorized, reply within them, list recent/subscribed activity, change supported thread notification/subscription levels, and navigate between root context and thread. Thread drafts and unread counts are distinct from the main composer. Do not simulate a server thread using a local-only grouping while claiming parity.

Acceptance: thread send includes the correct server relationship and appears in the same thread on another supported client. A missing `threads` capability hides thread creation; received unfamiliar thread data remains readable without flattening a reply into an unrelated send. Removed roots and inaccessible threads produce a clear unavailable state.

## MSG-007

**React without conflating reaction and chat permission (P1).** Add/remove one's own supported reaction and inspect permitted reaction authors. Optimistic changes reconcile with server counts and the current user's state. Separate call reactions from message reactions.

Acceptance: chat denied plus reaction allowed still permits reactions; the reverse does not. A revoked `react-permission`, deleted message, or failed request rolls back the pending reaction. Multiple clients and repeated clicks converge without inflated counts.

Provide three direct quick reactions on message hover or keyboard focus and a separate reaction picker, without requiring the context menu. Existing reaction badges toggle the current user's participation; an add-reaction control beside them opens the same picker. Reaction controls have transparent default backgrounds, including the add-reaction icon and unselected badges. Quick emoji suggestions use 14-point text and the palette uses 16-point text at the default scale, while pointer targets remain unchanged. Hover, keyboard focus and own-reaction selection stay distinguishable. The bounded Unicode palette highlights own reactions with a background instead of a permanent border, supports arrow-key selection and Escape, and returns focus to its invoker. It retires when its message, conversation, runtime or visible anchor is replaced. Reaction controls remain independent of send permission.

Remember the 12 most recently added Unicode reaction keys in device preferences, with duplicates moved to the front. The three quick suggestions use that order and fill unused slots with the standard defaults. Removing a reaction does not reorder the history. The bounded history survives restart and contains no message or account content.

At the default text size, reaction badges use a compact 24-point visual surface inside at least a 32-point hit area. Background, hover fill and keyboard focus follow the same visible boundary. Text scaling grows the badge without clipping its contents; pointer activation adds no focus outline. Apply the authoritative add/remove response directly to the scoped message instead of waiting for a second history request. Project the newest admitted desired state immediately. Older reads cannot revert confirmed counts or erase newer queued changes in the timeline or related message copies. A definitive failure rolls back the failed intent and shows a toast; uncertainty retains its pending identity without inventing server confirmation.

## MSG-008

**Edit and delete within actual policy (P1).** Offer edits and deletions according to message type, actor, moderator rights, capability, and current server limits. Show an edit mode and retained draft on failure. Distinguish delete message, delete rich-object share, and delete underlying file; never imply that deleting a chat share deletes the file everywhere. Honor note-to-self editing extensions only when supported.

Acceptance: expired edit/delete windows or a concurrent deletion produce explicit failure and a refreshed message. A successful edit shows server edit metadata; a successful delete updates timeline, previews, local search, pins, and cached excerpts. Do not hard-code an unlimited deletion/edit window from the version number.

Repeated Enter while an edit is staging retains the admitted request. A matching queued or server-accepted result may finish the edit mode; local staging is still distinct from server confirmation. Its completion can restore the prior draft only if the same editing context and submitted text are still present. Text typed in the meantime, or a cancelled and reopened edit, remains untouched; a failed edit keeps its text for deliberate recovery.

## MSG-009

**Mention, send silently, and show typing with privacy (P1 mentions; P3 silent send).** Autocomplete actual users and allowed room-wide mentions. Respect `mention-permissions`, `silent-send`, and typing privacy. Show the silent-send choice before submission; it is not the same as muting one's own notifications. Format federated/guest mention identifiers according to the server contract.

Acceptance: forbidden `@all` cannot be sent through a decorative mention control. Silent sends reconcile with their returned state; sharing media uses its own metadata/gates, not an assumed identical endpoint. Private typing preference emits no typing events, and typing expires on idle/disconnect without a permanent “schreibt …” label.

## MSG-010

**Read markers, unread state, and receipts (P1).** Mark read when the relevant conversation is actually presented and its content is visible under the client's reading policy; background prefetch, notifications, and search must not clear unread state. Distinguish unread counts, mentions, explicit “mark unread”, and optional common-read receipts. Respect read privacy and the server's session activity model.

Advance the read marker only to a message whose end has been painted inside the current conversation viewport, with the hidden pin-activity extension in MSG-012. This also applies to a short history that fits without scrolling. Replaced rows, hidden histories and a different account/runtime cannot reuse an earlier visibility observation. Busy local admission leaves the marker eligible for retry and does not display a send warning. Clear a room's unread count only when the acknowledged target covers its canonical event cursor, including omitted activity.

Acceptance: a hidden/minimized conversation does not become read from a background fetch. Turning read receipts off suppresses receipt display/transmission as required by the server contract. A common-read marker is never labeled as an exact individual reader list. Reconnect reconciles markers without resetting the user to a guessed latest message.

## MSG-011

**Search with scope and context (P1).** Provide conversation and account-wide message search through supported APIs, showing scope, query, progress, result snippets, and navigation to message context. Keep server search separate from an explicitly labeled partial local-cache search. Do not claim complete offline search. Where supported, add sender/date/type filters only with defined server semantics.

Acceptance: no matches, forbidden search, remote host failure, and incomplete offline results are different states. A result deleted or expired before opening reports unavailable; it does not reintroduce cached content. Search cannot reveal another account or restricted room through snippets or history.

Ctrl+F on Windows/Linux and Command+F on macOS opens or focuses conversation search below the header. Escape closes that search and returns focus without discarding a draft or leaving a call. Modal dialogs and IME composition retain their own input scope.

## MSG-012

**Pin messages (P3).** List pins, navigate to their context, and pin/unpin only when permitted and `pinned-messages` is advertised. Support a pin expiry and personal hide action when the applicable contract permits them; hiding a pin for oneself does not unpin it for everyone. Pins refer to canonical messages and do not override retention.

Acceptance: a pin creation failure does not leave a local pin presented as shared. A pinned message later deleted/expired becomes unavailable and is reconciled. A participant losing pin privileges retains only permitted read behavior.

Show pins in a compact banner directly below the chat header, with a pin icon and an action to reveal the selected message. Multiple pins have previous/next controls. Cycling uses one 170 ms transition. Pinning animates a decorative copy toward the header; unpinning shreds that copy without deleting the message. Put a small clickable unpin marker at the lower-right of each pinned row, beside delivery checks where present. Decoration retains at most 240 UTF-8 bytes, occupies one motion slot, expires within 450 ms and confers no server authority. Reduce Motion settles immediately; context, source, visibility or permission loss retires it. Missing painted geometry uses the static authoritative state.

Clicking a banner navigates smoothly to the canonical message. A context fetch waits for bounded row measurement before starting movement; manual scrolling cancels the movement. Redundant pin/unpin system notices are omitted from visible chat while retained for pagination and durable history. An entirely omitted page still exposes an explicit older-history action. A painted row's read target may extend through adjacent hidden pin activity only with observed page continuity; unrelated pages and unread ordinary messages remain barriers. Restored hidden tails require live revalidation through ordinary bounded polls; an unsuccessful repair of the same cursor has a 30-second cooldown. Reading pins and changing shared pins use separate permissions. The bounded pin list distinguishes loading, a confirmed empty result and failure, retaining confirmed entries during refresh. A read admitted before a successful pin change cannot reverse that change.

## MSG-013

**Remind later (P3).** Set/change/cancel a personal reminder for an accessible message, with local date/time selection and a visible upcoming-reminders list where available. The current backend uses supported server reminders. The chooser asks when to remind, without exposing server/local storage choices. Offer 30 minutes, one hour, tomorrow at 09:00 and next Monday at 09:00, plus a custom local date and time. Resolve calendar presets in the system timezone. Reject skipped clock times during daylight-saving changes and offer the first or second occurrence for repeated times. Closing the chooser preserves the draft and reply target. Scheduling uses the same chooser. A reminder never sends a message to other participants. Use server-confirmed timestamps and status.

An authenticated personal message-reminder notification uses the local important-notices policy, with its own typed reason and account/conversation target. Resolve it from supported server identifiers, never translated subjects or a local timer inferred from a message timestamp. Disabling local delivery does not cancel the server reminder or mark its message read.

Acceptance: ambiguous timezone/DST selection is resolved visibly; a failed creation does not promise a reminder. An inaccessible target opens a neutral unavailable state without its protected excerpt. Client quit does not imply a confirmed server reminder was canceled.

An empty write acknowledgement does not supply a reminder timestamp. Read the stored reminder before projecting its confirmed value. Changing or cancelling one reminder preserves other confirmed reminders; an unconfirmed follow-up read reports uncertainty without repeating the write.

## MSG-014

**Schedule messages on the server (P3).** With `scheduled-messages`, select date/time, inspect pending schedules, and edit/cancel according to actual API permissions. Clearly label scheduled versus sent. Do not replace server scheduling with an undocumented local timer that requires the client to remain running.

Acceptance: quitting after server confirmation preserves the schedule; a request timeout is reconciled before another schedule is created. A rejected schedule retains text. A server send failure, lost membership, or cancellation race appears as returned status without falsely claiming delivery or cancellation.

A confirmed cancellation removes only that scheduled entry from the local list.

## MSG-015

**Translate and summarize optionally (P4).** Offer message translation and unread-chat summaries only with supported APIs/providers and room policy. Show destination/provider information where available and require deliberate activation; never send private content to a third-party model chosen by the client. Keep original text available and label generated output. Summarizing does not mark unseen messages read automatically.

Acceptance: provider disabled/unavailable, unsupported language, task timeout, insufficient permissions, and classified/sensitive restrictions produce clear states. Generated text is not treated as authoritative conversation history; links to source context remain available when allowed.

## MSG-016

**Copy and forward deliberately (P3).** Permit copying text/links or forwarding selected content only when its room/security policy permits exposure and a supported destination send/share contract exists. A separate dialog names the account, previews the outgoing content, filters at most 100 loaded conversations of the same account, and requires destination selection followed by explicit confirmation. Preserve the composer and return focus to the originating timeline, thread or call chat on cancel. Revalidate the exact source, current permissions, session generation and destination before dispatch; stale controls cannot authorize a changed source. Forwarded content must not impersonate the original author; distinguish a new share/quote from the original message. Every ordinary action in the message menu has a matching icon.

Acceptance: cross-account forwarding is never an automatic side effect of switching accounts. An inaccessible or classified source cannot be exported through a forwarding shortcut. Missing attachment rights or an unavailable target preserves the user's choice with a clear failure. A failed forward does not remove or mark the source as sent to the destination. Clipboard use is explicit and subject to the security contract.

Forwarding acceptance belongs to the selected destination. It must not insert the forwarded message into the source timeline or reject a valid destination receipt because its conversation differs from the source. Deliberate message mutations surface their correlated failure or uncertainty; automatic observations cannot replace that feedback.
