# Server baselines and protocol sources

Target families are NextCloud 34 / Talk 24 and NextCloud 35 / Talk 25. The
executable [lab pins](../../tests/lab/pins.json) identify the 34.0.5 / 24.0.6 and
35.0.2 / 25.0.6 deployments. See [known limitations](../limitations.md) for
supported scope and [compatibility](README.md) for capability and policy rules.

The references below use immutable research commits `17afc250cf5fe3f7e016739dd3d7a3a44bb2cb79`
(Talk 24) and `f35255ab86f31e8ee894641f6970a09ce4b90927` (Talk 25). These are
branch snapshots, distinct from release commits `0d736588dcfb42becf0e5688e0847e35d5b5efa2`
and `eed360d176edcb6888dad60965cb694e6bf62ae3`. Source references establish protocol
provenance, not installed-server or native-client verification. Reconcile branch-only
behavior against the actual release before claiming support.

## Preset and policy precedence

The S05 parameter merge is default → selected preset → user changes → forced parameters. S20's creation path then enforces classified invariants: public type becomes private group, listability becomes none and SIP is disabled; a nonempty object binding is rejected. Thus forced values do not universally win. CONV-003 requires the review to show understood effective constraints and reconcile the actual returned room before success. S04/S20 and S09's chat controller establish all-role channel call denial, moderator-only member lists, non-moderator announcement leave denial and preserved deletion/history/public-link/listability locks. These are distinct from editable preset defaults.

Classified exposure guards were checked in the [invitation service](https://github.com/nextcloud/spreed/blob/f35255ab86f31e8ee894641f6970a09ce4b90927/lib/Service/InvitationService.php), [bot controller](https://github.com/nextcloud/spreed/blob/f35255ab86f31e8ee894641f6970a09ce4b90927/lib/Controller/BotController.php#L470-L482), [Matterbridge controller](https://github.com/nextcloud/spreed/blob/f35255ab86f31e8ee894641f6970a09ce4b90927/lib/Controller/MatterbridgeController.php) and S09/S20/S21 (including summary/private-reply restrictions). These support specific API restrictions, not universal protection against plugins or participants. CONV-004 separately labels stricter native cache/preview/export policy. S21's Talk25 consent validator returns early for classified rooms even under global-required consent; CALL-009 retains required consent everywhere it actually applies and never treats this exception as permission to record.

The [call-end listener](https://github.com/nextcloud/spreed/blob/f35255ab86f31e8ee894641f6970a09ce4b90927/lib/Listener/ClassifiedRoomAutoDeleteListener.php) marks an otherwise unbound classified room for the [object-retention job](https://github.com/nextcloud/spreed/blob/f35255ab86f31e8ee894641f6970a09ce4b90927/lib/BackgroundJob/ExpireObjectRooms.php). `retention_classified_rooms` is a configurable room-retention interval (reviewed default 3600 seconds; zero disables that sweep), independent of preset message expiry. Preservation does not bypass this automatic deletion. The moderator [keep/unbind operation](https://github.com/nextcloud/spreed/blob/f35255ab86f31e8ee894641f6970a09ce4b90927/lib/Controller/RoomController.php#L1176-L1197) changes `classified` to `classified_persist`, excluding that room from the sweep and re-queuing after later calls; classified restrictions remain. Neither setting promises universal preservation or an exact deletion instant.

## Re-ring authorization and response discrepancy

S07's pinned API prose says re-ring requires a moderator and lists an already-in-call target as `400`. S21's **both-family implementation** instead checks effective `START_CALL`, call-enabled policy and current call/participant state. Its target service accepts local/federated user actors in the same room, suppresses notification if any target session is already in call, and rejects a local DND target with `400`/`status`. An already-in-call target returns without notification and the controller can return `200`. Missing/wrong-room targets return `404`; unsupported actor types produce `400`/`actor-type`. Federated notification/status handling also depends on the supported proxy/host path.

MOD-002 follow those effective-permission and target gates, without adding a moderator-only client restriction. CT-016 must confirm response semantics on each release/profile before a compatibility claim; source behavior is not a completed live test. Unknown recipient availability is not denial inferred from an offline icon, and a successful request never proves delivery or that the recipient heard a ring.
